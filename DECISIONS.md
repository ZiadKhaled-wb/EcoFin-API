### D14. The service-role client is used only for pre-session auth steps

### D21. Incident: `EcoFin-Contracts` wiped by a worktree removal, rebuilt and verified (3 Oct, 12:06)
**What happened:** the master ran `git worktree remove --force` on an API worktree. On Windows, git followed the npm `file:` link `node_modules/@ziadkhaled-wb/contracts` (a junction) and deleted its **target**: the whole `EcoFin-Contracts` folder, `.git` included. The repo had never been pushed.

```bash
find <worktree> -path '<worktree>/.git' -prune -o -type l -print | while read -r l; do cmd //c rmdir "$(cygpath -w "$l")"; done
git worktree remove --force <worktree>
```
Publishing `EcoFin-Contracts` to GitHub (D1) removes the single point of failure.

### D24. Auth hardening found while building F04
- `must_change_password` is cleared only by the API, through the service-role client in `auth.admin.ts` (an extension of D14), **after** Supabase confirms the password change. The DB function isn't executable by `authenticated`, so a user can't clear the flag directly through PostgREST.
- Local `jwt_expiry` is 900 s (15 min). A logged-out access token is refused by the API at once, but PostgREST accepts it until it expires, so a short expiry narrows that window. **Production:** set the same JWT expiry in the Supabase project settings.
- `/refresh` has its own generous per-IP limiter (not the login limiter), so silent refreshes from one shop IP can't block logins.
- The error handler recognises zod errors by name, as well as with `instanceof`, because the contracts package carries its own zod copy.

### D25. Follow-ups from the F04 review
- **Per-request status gate (F05):** employee active, shop active, subscription not ended and `must_change_password` are re-checked on every request, not just at login, because a token can be obtained straight from GoTrue with the public anon key.
- D14 is extended: change-password also counts failed current-password checks in `login_attempts` through the service role (D17 lockout).
- **Known, accepted for now:** an authenticated user can call `auth_record_login` / `auth_record_logout` directly through PostgREST and forge the `x-forwarded-for` / `user-agent` that `app.write_audit` stores. That's a baseline-wide property of `write_audit` reading request headers. **Follow-up:** have PostgREST behind the API only (no public PostgREST access), or sign the client-IP header.
- **Known, accepted for now:** login lockout is check-then-act, so a parallel burst from many IPs can slightly exceed the limit. An unknown username answers a little faster (timing). Both are low risk; revisit in hardening.

### D31. F12 money: big.js in the contracts package, half-up, tax rounded per line (user decision on the library, 4 Oct)
- **Library** (user decision): `big.js` 7.0.1 (small, no dependencies, exact decimals, half-up built in), a runtime dependency of `@ziadkhaled-wb/contracts` so API and Web share one implementation (contracts 0.4.0; `@types/big.js` is a dev dependency, the published types don't expose big.js). The module uses its own big.js constructor in strict mode, so a JS number passed by mistake throws and nobody else's global settings apply.
- **Strings only**: helpers take and return decimal strings (the contract's `Money`); results always have exactly 2 decimals and never read "-0.00". add/subtract/sum accept only values with at most 2 decimals, so rounding can't hide inside a sum; a result that doesn't fit `numeric(18,2)` throws.
- **One rounding rule**: half-up to 2 decimals (a half rounds away from zero: 2.345 -> 2.35, -2.345 -> -2.35).
- **Line level, defined once**: tax is calculated and rounded per line (T01 says line-level); document totals are sums of the rounded lines (`sumTaxLines`) and are never re-taxed. Prices without VAT: tax = round(net x rate%). Prices with VAT: net = round(gross / (1 + rate%)), tax = gross - net, so net + tax = gross exactly. Rates are percentage strings like the `tax_rate numeric(5,2)` columns ("14"). T01 checks these rules against the ETA rounding cases with the client's accountant and may refine them.
- **Exact splits**: `splitMoney` / `allocateMoney` use the largest remainder method in piasters: the parts always add back exactly, leftover piasters go to the largest remainders and ties to the earlier part (1000.00 / 3 = 333.34 + 333.33 + 333.33). Use `allocateMoney` to spread a document discount across lines (T01) and `splitMoney` for installment schedules.
- **Formatting**: `formatEgp(value, 'ar' | 'en')` = Latin digits with the locale's separators, currency after the amount ("1,250.50 EGP" / "1,250.50 ج.م"), rounded half-up first; EcoFin-Web's `formatMoney` uses it.

### D32. F11 numbering: yearly sequences as in the baseline, proven with pgbench (user decision on the format, 4 Oct)
- **Format** (user decision): keep the baseline's `<branch code>-<type>-<yy>-<6 digits>`, e.g. `BR1-SL-26-000123`, one sequence per shop, branch, document type and year (restarts at 000001 each year in the shop's time zone, data model §12). The slice's `BR1-RC-000123` was an example; no migration.
- **How it stays unique and gap-free**: write functions call `app.next_document_number()` inside the transaction that inserts the document. The counter row stays locked until commit, so concurrent documents wait their turn, and a rolled-back document rolls its number back (the next document gets it). Numbers taken outside the document's transaction would leave gaps: don't.
- **Proof**: `supabase/tests/f11_numbering_test.sql` (format, separate sequences, yearly reset, rollback reuse, other shop's branch refused, unique prefix per document type, no direct access) and `npm run db:numbering` (`scripts/db-numbering-proof.mjs`): 1,000 concurrent creations from 40 pgbench sessions, with 400 rolled-back ones mixed in, give exactly 000001..001000, unique, in the order handed out. pgbench ships in the Supabase database image, so there's no new dependency. Both run in the CI `db` job.
- **Test cleanup**: shops, branches and counters can't be deleted (NO_DELETE triggers). The proof's throwaway fixture is removed with triggers off for that one local transaction (`SET LOCAL session_replication_role = replica`); never do this outside local tests.

### D33. F10 ledger core: reconciliation check, idempotency lock for write functions, proven with pgbench (user decisions, 4 Oct)
- **What was already there** (baseline section 17): append-only `stock_movements`, `cash_movements`, `store_credit_movements`; the caches `stock_levels`, `cash_balances`, `store_credit_balances` are changed only by the AFTER INSERT triggers, under a row lock; no overselling (reserved stock counts as taken), no safe/drawer/wallet below zero, a movement reversed once at most, idempotency keys unique per shop on every document table. App users can't write any of these tables.
- **Reconciliation** (migration `20261003120000_f10_ledger.sql`): `app.ledger_mismatches(org DEFAULT NULL)` returns one row per cache that doesn't equal its ledger (stock on hand per product/branch/state, reserved vs active reservations, cash per account, store credit per customer; a cache or ledger side that's missing counts as 0). **Internal only** (user decision): not granted to app users; CI runs it (`npm run db:reconcile`) after the full test suite; the nightly job (F13) and monitoring (Q02) will run it. No endpoint and no permission key.
- **Idempotency lock**: `app.lock_idempotency_key(org, key)` (8-128 characters, else `VALIDATION_FAILED`). Every money/stock write function calls it FIRST, then returns the existing document for that key if there is one, and only then takes the document number and posts. Concurrent requests with one key queue on the lock, so the second returns the first one's document: nothing is posted twice and no number is wasted. Without it, the second request would fail on the unique key after already taking a number (the proof shows this). Same key with a different body (`IDEMPOTENCY_CONFLICT`) is for each write function to check.
- **Proof** (user decision: a test-only sale, since the real `post_sale` is S01): `npm run db:ledger` builds a throwaway shop with 10 units and a sale routine in a scratch schema that follows these rules on the real `sales`, `stock_movements` and `cash_movements` tables. 100 requests from 50 concurrent sessions sell exactly 10; the other 90 get `OUT_OF_STOCK` and leave no sale, movement or number. 50 concurrent requests with one key make one sale, one stock and one cash movement. Then everything reconciles. S01 should run the same proof against its real function. `supabase/tests/f10_ledger_test.sql` covers the single-session rules.
- **Shared proof helpers** in `scripts/db-proof-lib.mjs` (psql/pgbench through `docker exec`, throwaway-shop cleanup with triggers off for that one local transaction). The F11 proof uses them too.

### D34. F13 background jobs: the baseline queue, a worker inside the API, logs for now (user decisions, 5 Oct)
- **Queue**: the baseline `public.jobs` table (statuses queued/running/succeeded/failed/dead, attempts, `max_attempts`, `dead` = the failed list). Migration `20261003130000_f13_jobs.sql` adds service-role-only functions the API calls through PostgREST: `jobs_enqueue_daily`, `jobs_claim` (the `app.claim_jobs` rules plus a filter on the job types the worker has handlers for, so a server that doesn't know a type, e.g. an older version during a deploy, never takes it), `jobs_succeed`, `jobs_fail`, `jobs_ledger_mismatches`, and the read-only support view `app.v_job_runs`. No pg-boss, no pg_cron, no direct Postgres connection.
- **Scheduler** (user decision: API ticker): `src/jobs/worker.ts` runs inside the API (`JOBS_ENABLED`, default true; `JOBS_POLL_SECONDS`, default 30). Each tick asks `jobs_enqueue_daily` to queue each daily job for every active shop whose local time (`organizations.timezone`, Africa/Cairo by default) is past the job's start time. It holds a per-type lock and skips shops that already have that day's run in ANY status, so a daily job runs once per shop per local day however many API instances tick. Shops with an unknown time zone are skipped, not fatal.
- **Retries**: a failed attempt waits 1, 2, 4 ... minutes (at most 1 hour), then the last attempt (`max_attempts`, default 5) makes the job `dead`. A worker that stalls for 15 minutes loses the job to another worker, and only the holder can finish it. Handlers must be safe to run twice.
- **Visibility** (user decision: log now, screen later): every run, retry and dead job is one structured log line (job id, type, shop, attempt, worker); a dead job logs at error level. ### D48. I02 stock adjustments and counts: reasons set the direction, counts post against the live stock (EC-48, 10 Oct)
- **Adjustment** (`POST /api/stock/adjustments`, `stock.adjust`, `Idempotency-Key`): a branch, a reason, an optional note (required for `other`, at most 500 characters) and 1-500 lines (product, unit for serialized products, ± quantity). **damage and loss only remove stock, found only adds it, correction and other go either way** (`ADJUSTMENT_SIGN_INVALID`); `count` is used only by a posted count. Numbered `SA` (F11), posted once (append-only; a mistake is fixed by another adjustment). Each line inserts one `stock_movements` row (type `adjustment`, source the adjustment and its line, cost = the unit's cost or the product's average cost) in product, then unit order; the triggers keep `stock_levels` and the unit (a removed unit becomes `written_off`, a found one `in_stock` here). **A unit comes back into stock only from `written_off`**: a sold, returned-to-supplier or in-repair unit is refused (`UNIT_NOT_AVAILABLE`), by an adjustment and by a count (security review, 10 Oct). Sellable stock only; damaged stock (S05 returns) is not adjusted here.
- **Count** (`stock.count` for everything, including posting; WAREHOUSE has it, not `stock.adjust`): a sheet for a branch, optionally one category with its subcategories (D42). Created with a snapshot of lines: one per non-serialized product in scope (active, or archived but still holding stock there) and one per serialized unit in stock or reserved in the branch. **Counts that cover the same products can't be open together in a branch** (`STOCK_COUNT_OPEN`; a whole-branch count overlaps everything). Counted quantities are typed (`PUT .../lines`, null = not counted) or scanned (`POST .../scan`: a serial counts its unit; a barcode or SKU adds one; a serialized product's barcode is refused). A product or unit in scope that isn't on the sheet is added when counted; a unit in stock in another branch is refused (that's a transfer).
- **Posting** (`POST .../post`, `Idempotency-Key`): **expected = the live stock, not the snapshot**. Posting locks the units and stock rows (product order, as the ledger triggers do), stores the expected quantities, and posts every difference as **one adjustment** (reason `count`, linked to the count). Afterwards the stock equals the counted numbers, even if a sale happened while people were counting (the screen shows the live expected quantity, so the difference shown is what posting will change). Uncounted lines block posting (`STOCK_COUNT_INCOMPLETE`) unless the caller sends `uncounted_as_zero` (then they're treated as missing). A count with no differences posts without an adjustment. Posting or cancelling again answers the same result; a posted count can't change or be cancelled (`DOCUMENT_FINAL`).
- **Audit**: `stock_adjustment.posted` (lines in `after`, note as the reason), `stock_count.created`, `stock_count.posted` (the adjustment and its lines), `stock_count.cancelled`. Saving or scanning lines is draft data and not audited (registry entries with a reason).

### D49. I03 branch transfers: draft, sent, received; shortages are adjustments at the destination (EC-49, 10 Oct)
- **States**: `draft` (lines editable, nothing moves) -> `sent` -> `received` or `partially_received` (both final); a draft can be `cancelled`. A **sent transfer can't be cancelled** (`TRANSFER_ALREADY_SENT`): receive it with shortages, or send the goods back with a new transfer. Numbered `TR` in the source branch (F11).
- **Who**: draft, edit, send and cancel need `stock.transfer_send` and the **source** branch (the destination can be any active branch: `GET /api/stock/transfers/destinations`, since `GET /api/branches` lists the caller's own branches only; transfers carry both branch names for the same reason); receive needs `stock.transfer_receive` and the **destination** branch (WAREHOUSE has both). Reads need `stock.view` and either branch; they also work in an expired (read-only) shop.
- **Stock**: send posts a `transfer_out` per line at the source (a unit becomes `in_transit`); the quantity shows as **in transit** at the destination (I01, `v_stock_in_transit`: lines of `sent` transfers). Receive posts a `transfer_in` of the **full quantity sent** at the destination, then writes off what did not arrive (`loss`) or arrived broken (`damage`) with an adjustment per reason at the destination (note `Transfer <number>`). So stock is always at the source, in transit or at the destination, and every missing unit has an adjustment with its reason (the Done when, proven in `i03_transfers_test.sql`).
- **Idempotency**: create takes the `Idempotency-Key`; send, receive and cancel are state changes under a row lock, so a repeat answers the transfer and moves nothing. ### D60. K02 shifts: a drawer per cashier, floats as cash transfers, differences booked at closing (EC-60, task decisions 10 Oct)
- **Numbers:** contracts **0.28.0**, **D60**, migration `20261011160000_k02_shifts.sql`, 7 routes under `/api/shifts` (146 in total). No spec file was written for K02; these are the build's decisions, and the ones marked *default* are to confirm with the owner.
- **Done when, how it holds:** every cash movement of a shift carries `shift_id` on the shift's **drawer** account, so expected cash = the shift's drawer ledger sum (the float is its first row), never the safe. A new trigger (`trg_cash_movements_c_shift`) refuses a movement tagged with a shift unless that shift is open and the account is its drawer (`SHIFT_CLOSED`), so a closed shift can take no sale; S01 calls `app.require_open_shift` (`SHIFT_REQUIRED`).
- **The drawer** (*default*): one drawer account per cashier per branch, created at the first shift (`درج <name>`) and reused afterwards; it is at 0 between shifts. K01's screens don't list drawers.

One open shift per cashier and per device (`SHIFT_ALREADY_OPEN`; the baseline unique indexes are the last line). The float and the closing use reserved keys (`system:shift-open:<id>`, `system:shift-close:<id>`).
- **During the shift:** `POST /api/shifts/:id/cash` moves cash `in` (change from a safe) or `out` (a cash drop into a safe) with a note (3-500); neither side goes below 0 (`INSUFFICIENT_FUNDS`). Idempotent by key.

Reads: `shift.operate` sees own shifts, `cash.view` every shift of the caller's branches, also in an expired shop; others → `SHIFT_NOT_FOUND`. `GET /api/shifts/vaults` lists the branch's safes by name only (a cashier doesn't see balances).

### D62. S01 sale core: one transaction per sale, in the cashier's open shift, priced by the server (EC-68, task decisions 10 Oct)
- **Numbers:** contracts **0.30.0**, **D62**, migration `20261012090000_s01_sale_core.sql`, 3 routes under `/api/sales` (159 in total). Spec: `docs/tasks/S01.md`. No new tables, columns or enums.
- **Done when, how it holds:** (1) a sale writes only through the ledgers, so every stock level and cash balance still equals its ledger sum and `app.ledger_mismatches()` stays empty, and the sales' totals equal their payments and the drawers' `sale` movements; (2) a repeated `Idempotency-Key` answers the first sale before anything else is checked, under the key's advisory lock, so a double submit makes one sale; (3) the cart's unit rows and stock rows are locked before availability is checked, and the ledger trigger refuses again, so the last unit is sold once.
- **Where a sale lives:** in **the caller's open shift** (`SHIFT_REQUIRED`). The request carries no branch: the shift gives the branch, the device and the drawer. The shift row is locked for the sale, so it can't be closed halfway (`SHIFT_CLOSED`).
- **Prices come from the server.** The list price is `products.cash_price`. A line's `unit_price` is only read when it differs, and then the caller needs `price.override` (`PRICE_OVERRIDE_DENIED`, 403); overridden lines are listed in the audit row, which becomes a warning. The body carries `expected_total`, the total of the quote the cashier confirmed; a different server total → `PRICE_CHANGED` (409, both totals) and nothing is sold.
- **Order inside the transaction:** permission and module (`sale.create`, `pos`) → idempotency lock and replay → cart shape → shift lock → customer → lock units (by id) then stock rows (by product id) → price and tax the cart on what is committed now → total above 0 → `expected_total` → availability per product (`OUT_OF_STOCK`, 409, details `product_id`, `requested`, `available`) → number (SL) → sale, lines, stock ledger rows → payment → audit. Everything refused happens before the number is taken; a failure after it rolls the counter back with the rest.
- **Locks in one fixed order** (units by id, then stock rows by product id), so two tills with the same products in different cart orders can't deadlock each other. Proved by `npm run db:stock-cash` rounds F to I (four cashiers, 20 sessions).
- **Tax:** `app.compute_document_tax` with the shop's `prices_include_vat` and each product's tax class rate at the moment of sale; the sale keeps the snapshot (mode, per line class, rate, tax, total), so later setting changes don't touch old sales. Discounts are S03: zero here.
- **Serialized products:** the line names the unit; it must be that product's, `in_stock` in the shift's branch. A unit **reserved** for an order is not sold to a walk-in (`UNIT_NOT_AVAILABLE`), although the baseline trigger alone would let it out. The trigger marks the unit `sold`.
- **Cost and warranty snapshots:** `sale_lines.unit_cost` is the unit's cost for a serial, else the product's average cost; `sales.cost_total` is their sum. `warranty_until` = sale date + the product's warranty months when above 0. Costs never leave the server in a quote or a sale.
- **Money (S01):** the whole total in cash: one `payments` row (PY, key `system:sale:<id>:1`), its allocation to the sale and one `sale` cash movement on the shift's drawer tagged with the shift, so the shift's expected cash rises by the total. This step is `app.post_sale_payments`; S02 replaces it with payment lines.
- **Reuse:** `public.post_sale` is thin; `app.post_sale_core` does the work for a caller that already holds the permission, the key lock and the locked shift. N02 and S10 call the core with their own payment step.
- **Quote** (`POST /api/sales/quote`): the same checks and tax engine, nothing locked or written, `available` reported per line instead of enforced. It needs the open shift too (the branch comes from it). A read: works in an expired shop; not audited.
- **Reads:** the caller's own sales with `sale.create`; with `report.view` or `cash.view` any sale of the caller's branches; others `SALE_NOT_FOUND`. Lists, search and void are S07.
- **Differences from the spec:** a sale's lines don't repeat `list_price` / `overridden` (they aren't stored; the override is in the audit row); the quote needs the open shift; `MODULE_NOT_IN_PLAN` can't be tested because every plan has the `pos` module today.
- **Left to later slices:** other payment methods and change (S02), discounts and on-the-spot approval (S03), receipts (S04), ETA receipts (T02: no fiscal document is written yet), returns (S05), void (S07). A total of 0.00 is refused.
- **Known limit:** a sale and another kind of document (a multi-line adjustment or transfer) can still lock the same stock rows in different orders; PostgreSQL then ends one of them with a deadlock error, which the API reports as a failed request to retry. Nothing is half-written. Aligning the lock order of adjustments and transfers is a follow-up.

### D69. O03 POS devices: a computer is a device by a token the API resolves, never by an id it sends (EC-146, task decisions 13 Oct)

The API has the limiter (429), and `pair_device` counts failures itself in `device_pairing_attempts` (same review: the function can be called without the API): a failure answers NULL instead of raising, because an exception would undo the count, and after 5 failures in a minute the code is not looked at. Relations: father, mother, brother, sister, spouse, son, daughter, relative, friend, colleague, employer, neighbour, other (checked in the function, no enum). ### D72. R03 credit profile and limit: an explicit limit, one check in the database, exceptions as approvals on the spot (EC-65, task decisions 15 Oct)
- **The limit is explicit.** `customers.credit_limit` is the only limit the server uses; a new customer has 0, so no installment sale passes without a limit or an exception. `suggested_limit` = monthly income x `credit_limit_income_multiple`, rounded down to the pound (null when either is missing), is shown in the profile and prefills the dialog but is never used by the check (*to confirm*: the alternative is "0 means use the suggestion"). R01's `update_customer` still refuses `credit_limit`.
- **Setting it:** `set_customer_credit_limit` (`credit.approve`, plan module `customers`): 0 to 99 999 999.99; a reason of 3-300 is required only when the limit goes up (`CREDIT_REASON_REQUIRED`); the same value again changes nothing and writes no audit row; a limit below the exposure is allowed (the customer just can't take more); archived customers are refused (`CUSTOMER_BLOCKED`, no `CUSTOMER_ARCHIVED` code exists). History = the last 10 `customer.credit_limit_set` audit rows (no new table).
- **Exposure and available** come from `v_contract_balances` (the same sums as `v_customer_exposure`: unpaid principal of `active` and `rescheduled` contracts, superseded lines out). Available = limit - exposure; the profile shows it **never below 0** and puts the excess in `over_limit_by`; the check compares with the true difference.
- **Score** (0-100, integer, half-up, read only, nothing stored) = sum of the shop's `credit_score_weights` x four components in 0..1: guarantors (active, not archived, linked guarantors / 2, at most 1), income (1 when monthly income > 0), identity (0.5 for a national ID that parses + 0.5 for at least one F14 ID photo), residence (0 until R05: `TODO(R05)` in `app.customer_credit_score`). The profile returns each component with its weight and points, and `min_score`.
- **Behaviour** (`app.customer_credit_behaviour`) over the customer's current, non-superseded schedule lines that are due (due date <= today in the shop's timezone), migrated contracts included: `on_time_pct` (whole percent of the lines whose payments up to the due date, by the payment's business date, cover them), `max_days_late` (the day a line was fully paid, or today while it is not, minus its due date), `current_overdue_amount`, `overdue_lines`, open and completed contracts. Null where nothing is due.
- **The check** `app.check_customer_credit(org, customer, financed, approval)` (not granted; N02 calls it in its transaction; it locks the customer) raises in this order: `CUSTOMER_NOT_FOUND`; `CUSTOMER_BLOCKED` (blocked or archived, never overridable); then the reasons `limit` (financed > available), `score` (< `credit_min_score`), `watch` (status watch): `CREDIT_LIMIT_EXCEEDED` (when `limit` is among them), else `CREDIT_SCORE_TOO_LOW`, else `CREDIT_CUSTOMER_WATCH`, all with the details `{limit, exposure, available, requested, score, min_score, reasons}`. With no reason it returns NULL (an approval passed in is ignored). With one the approval must be kind `credit_exception`, this shop and customer, `approved`, unused, decided within 24 hours and for at least the financed amount, else `CREDIT_APPROVAL_INVALID`; it returns the approval's id and N02 then calls `app.use_credit_approval(approval, contract)` (writes the contract id into `entity_id` once).
- **Exceptions are approvals on the spot (copied from S03):** `request_credit_exception` (`sale.create` or `credit.approve`; reason 3-300; stores limit, exposure, available, score and reasons at request time; `APPROVAL_NOT_NEEDED` when the sale would pass anyway), `decide_credit_exception` (`credit.approve`; the requester can't decide their own request unless the decider is the OWNER (*to confirm*); a rejection needs a note; approving a customer blocked meanwhile is `CUSTOMER_BLOCKED`), `cancel_credit_exception` (only the requester, while pending), `get_credit_exception`, `list_credit_exceptions` (pending first). Valid **24 hours** after the decision (*to confirm*; S03 uses 15 minutes for a cart) and for one contract. `app.approvals_freeze` is re-created from its S03 version with `credit_exception` added next to `discount_above_cap` for the one write of `entity_id`.
- **Safety net:** a deferred constraint trigger `trg_contracts_credit_check` on `contracts` takes the customer lock and, at commit, recomputes the exposure **without** the new contract and refuses `CREDIT_LIMIT_EXCEEDED` unless an approved `credit_exception` approval has `entity_id` = the contract and an amount of at least its financed amount; `CUSTOMER_BLOCKED` for a blocked or archived customer; migrated (M02) contracts are exempt. It checks the limit and the customer's state only; the score and watch reasons are enforced by `app.check_customer_credit`, as the spec says. This makes "the server blocks an installment sale over the limit even if the client sends it directly" true for any writer.
- **Preview** `get_customer_credit_check` answers instead of raising for the credit reasons: `allowed`, `reasons`, `needs_approval`, the numbers, `pending_approval_id`, `approved_approval_id`; a customer not found, blocked or archived still raises.
- **Where I left the spec:** (1) the baseline `CHECK approvals_check1` (decided_by <> requested_by) made the owner deciding their own exception impossible, so it is replaced by `approvals_no_self_approval` that exempts the kind `credit_exception` (the function refuses everyone but the OWNER with `APPROVAL_SELF`); this is the one change to a baseline table in an otherwise table-free migration. (2) `p_reason` of `set_customer_credit_limit` has `DEFAULT NULL` (a lowering needs none). (3) `CREDIT_REASON_REQUIRED` (400) is its own code, not `VALIDATION_FAILED: reason`. (4) A request for an exception that would pass anyway answers `APPROVAL_NOT_NEEDED` (S03's code). (5) Exception rows have no branch (`branch_id` NULL): a credit limit belongs to the customer, not to a branch. (6) The profile shows `available` clamped at 0 (decision 4 says "shown as 0"). (7) `value` of a score component is rounded to 2 decimals in the answer; the points and the score use the unrounded value.
- **Not built:** the installment sale and contract (N01/N02), the survey score (R05), automatic limit changes from behaviour, a stored score, a credit bureau lookup.
- **Numbers:** contracts **0.42.0**, migration `20261016090000_r03_credit_profile.sql`, 8 new routes (221 in total on top of R04's 213), audit actions `customer.credit_limit_set`, `credit_exception.requested`, `credit_exception.approved`, `credit_exception.rejected`, `credit_exception.cancelled`, new error codes `CREDIT_LIMIT_EXCEEDED`, `CREDIT_SCORE_TOO_LOW`, `CREDIT_CUSTOMER_WATCH`, `CREDIT_APPROVAL_INVALID`, `CREDIT_REASON_REQUIRED`.
- **Left to later slices:** calling the check and attaching the exception in the installment sale (N02, `app.use_credit_approval`), the survey part of the score (R05), the customer account page (R02), the POS screen asking for an exception (N02 reuses the Web dialog).

### D74. R02 customer account: read only, one open-balance formula, a statement whose closing balance matches the account (EC-64, task decisions 15 Oct)
- **Read only.** No table, column, enum, view or permission change. Three read functions (`get_customer_account`, `get_customer_contract_schedule`, `customer_statement`) and seven `app` helpers, nothing stored, no audit row. Reads use the R01 read guard (`app.customer_read_guard`: any customer read key of D63 and the plan module `customers`); an expired shop reads (*to confirm*: the alternative is to limit the money parts to `credit.approve`, `collection.create`, `installment.create`, `customer.edit`, `report.financial`).
- **Contract total** (`app.customer_contract_total`) = the current (not superseded) schedule lines' amounts + what was paid on superseded lines, so the formula stays true after a reschedule (N05). For a contract never rescheduled it equals `total_payable`; a contract with no schedule lines counts its `total_payable`.
- **Open balance (the slice's Done when)**, over `active` and `rescheduled` contracts (`app.customer_open_balance`): contract totals − payments (`v_effective_allocations` on their schedule lines, so a reversed payment drops out) − returns (`sales_returns` with `refund_method = contract_adjustment` on their sales). With no contract-adjustment return the open balance equals the sum of `v_contract_balances.remaining`; `TODO(S05/N05)`: such a return must also write the new schedule version so both keep agreeing.
- **Overdue** from `v_contract_balances` and `v_receivables_aging` (open contracts only): amount, lines, max days late, `next_due_date` = the earliest unpaid current line (it may be in the past) and `next_due_amount` (what is left on the lines due that day), the five aging buckets.
- **Account:** customer head (no national ID), balance (+ store credit, R03's limit and available clamped at 0), overdue, totals (purchases = sales not voided; returns = returns, voids and exchanges; payments in / out = cash and bank transfer payments that were not reversed: store credit is not money in), every contract newest first, the last 10 effective payments with what they paid (a schedule line is "contract #seq"), the last 10 returns, and the count of files on the customer and its contracts. Purchases (S07 `GET /api/sales?customer_id`), guarantors (R04) and documents (`GET /api/files`, entity types `customer` and `contract`, both already allowed) are not repeated.
- **Schedule:** the contract (same object as in the account), its lines (current version first, then superseded ones, with `days_late` only when overdue) and its charges with waived, paid and due. A contract that is not the customer's → `CONTRACT_NOT_FOUND` (new, 404).
- **Statement** (shop-wide, dates in the shop timezone, balance > 0 = the customer owes): debits = every sale (a void is its own return row), a contract's total above its financed amount when it has a sale (the markup, plus what a reschedule added; a contract without a sale, M02: its whole contract total), payments out (refunds), late fees, reversals of payments in; credits = payments in, returns / voids / exchanges, fee waivers, reversals of payments out. **Store-credit payments, in or out, are not rows:** the credit was counted when it was given (by the return or the overpayment), so without dates the closing balance equals `total_due − store_credit`; the SQL test checks this on every customer it builds. Rows sort by date, creation time, then sale → contract → payment → return → fee → waiver. `from > to` or more than three years → `VALIDATION_FAILED` (*to confirm*: three years). `TODO(S10)`: order deposits; `TODO(N05)`: write-offs and early-settlement discounts become credit rows.
- **Where I left the spec:** (1) every sale is a debit row, voided ones too (the spec said "not voided"; without the sale the void's credit row would not net out). (2) The contract row is "contract total − financed amount" rather than the markup alone, so a reschedule that adds profit still matches the account. (3) `payments_in` / `payments_out` leave store credit out, like the statement. (4) `files.service.ts` already allowed `entity_type = 'contract'`, so it is unchanged. (5) Printing the statement is not logged (*to confirm*; S04 logs receipt prints, a statement is not a fiscal document).

### D76. N01 installment rules engine: one calculation in SQL with a TypeScript copy, a fixed deferred price, commit-time safety nets (EC-80, owner decisions 15 Oct)
- **Islamic finance (owner decision):** an installment sale is a sale at a fixed deferred price, not a loan (`docs/ISLAMIC_FINANCE_RULES.md`). The engine produces one installment price per contract, fixed at signing; nothing is a rate on time; the user-visible word is "profit" (ربح), never "interest". To be confirmed with Dar al-Ifta or a Sharia advisor before going live.
- **Where the calculation lives (D41's pattern):** `app.installment_terms(policy, input, today)` is the source of truth (pure: same inputs, same answer); `computeInstallmentTerms` in the contracts is the same calculation for screens. Both run 35 golden cases (`supabase/tests/fixtures/n01_terms_cases.json`); the SQL test embeds a copy and `src/test/n01-golden.test.ts` keeps it equal. Money is `numeric` in SQL and big.js in TS.
- **Terms (owner, 15 Oct):** financed = cash price − down payment; the markup % is the first tier whose `up_to_months` covers the plan's duration and is the profit for the **whole term**; markup = round(financed × % / 100, 2) half-up; total = financed + markup. Duration: monthly = n, weekly = ceil(7n / 30), daily = ceil(n / 30). Installment = total / n rounded **up** to a multiple of `rounding_step` (n = 1: the total); the last line takes the rest (≤ 0 is the violation `rounding`); rounding never moves the total or the markup. The markup is spread over the lines in proportion to their amounts (largest remainder in piasters, ties to the earlier line); principal = amount − profit.
- **Dates:** the first due date defaults to one period after the sale (monthly: same day next month, month end clamped) and must be after the sale day and at most 60 days later; line k is due k − 1 periods after the first (months counted from the first date each time, so 31 Jan → 28/29 Feb → 31 Mar).
- **Rules, reported as violations (the preview answers them; the confirm side raises `INSTALLMENT_TERMS_INVALID` with the list):** `frequency_not_allowed`, `sale_below_minimum`, `down_payment_too_high` (at or above the cash price, or above `max_down_payment_pct`), `down_payment_too_low` (the frequency's rule: `percent` = `min_down_payment_pct` half-up; `one_installment` = at least one installment; `installment_per_day_of_month` (daily) = one installment per day of the month so far; the installment rules replace the %), `too_many_months` (`max_months` and the first `amount_tiers` entry covering the cash price), `installment_below_minimum` (the higher of `min_installment` and the frequency's minimum; the smaller last line is exempt), `rounding`, `first_due_date_out_of_range`. `min_down_payment` in the answer is the smallest passing down payment (a bounded search in piasters for the installment rules).
- **Confirm side for N02:** `app.check_installment_terms(org, input, policy_version)` (not granted): `POLICY_NOT_SET` (409), `POLICY_CHANGED` (409, `{current_version}`) when the POS previewed another version, `INSTALLMENT_TERMS_INVALID` (400, `{violations}`); returns the terms N02 stores (contract columns and version-1 lines).
- **Safety nets at commit (any writer):** `trg_contracts_terms_check` (deferred, non-migrated contracts): the contract's policy must be the shop's current version (`POLICY_CHANGED`), the engine run for the contract's own columns on the shop date of `created_at` must have no violation and must give exactly its `markup_pct`, `markup_amount`, `total_payable` and version-1 lines (`INSTALLMENT_TERMS_INVALID`, `{mismatch}`). `trg_schedule_lines_sum_check` (deferred, all contracts, version 1): Σ amount = total, Σ principal = financed, Σ profit = markup, seq 1..n (`SCHEDULE_NOT_BALANCED`, 409). `TODO(N05)`: later versions; a reschedule never increases what is owed. A policy published after a contract never touches it.
