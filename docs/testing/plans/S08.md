### Where S01's core is

`app.post_sale_core` exists already (S01 created it, S02, S03 and N02 replaced it; N02's body is the latest).
`public.post_sale` (S03), `public.post_installment_sale` (N02) and S05's exchange call it. So D12.7 is "call the
core". A trailing parameter on `app.post_sale_core` itself would change the signature the S01 and N02 SQL tests
call directly, so the body moved to `app.post_sale_core_full` and the old name stays a wrapper. Its `sale_cart` prices from the products of today and its number,
time and day come from the counter and the clock; an offline sale must end identical to the printed receipt, so
those values come from `p_offline`.

### What T02's loaders do with offline (non-head) rows

- `eta_load_pending_for_device` (prepare) loads only rows with `eta_uuid IS NULL`. An offline fiscal row is
  inserted with its UUID, so prepare never builds or re-chains it.
- The POS chain head (`devices.eta_last_uuid`) is moved by receive (D8) to the last offline UUID; the next online
  sale is then prepared by T02 with that `previousUUID` (I10). A fork (the offline chain did not start at the
  head) is logged as `chain_fork` and the head still moves: the ETA checks only the format of `previousUUID`.
- `eta_claim_for_submit` sends every pending row that has a UUID, in issue order, whatever the head is: it is
  the one loader that needed a change (D12.2), so a held or unprocessed offline row is never sent.
- `eta_store_prepared`'s compare-and-set only concerns prepared (online) rows; receive moves the head under the
  device row lock (`FOR UPDATE`), so a concurrent prepare gets `CHAIN_MOVED` and builds again.

### Differences from the task file (noted, followed as written below)

1. **Service-role functions** live in `app.` (`app.offline_load_received`, `app.offline_process`), granted to
   `service_role` only. PostgREST exposes only `public` (T02's note, D67), so the worker reaches them through
   two thin `public.offline_worker_*` wrappers that are also granted to `service_role` only, exactly like T02's
   `eta_*` worker functions.
2. **`post_to_shift` to another drawer:** EC-147's `sales_device_from_shift` gives a sale its shift's device,
   so a sale posted to another shift carries that shift's device. The fiscal row keeps the offline device (the
   receipt was issued by it and is in its chain).
3. **"the target shift's open business day"** (late business date): shifts have no business date of their own;
   an open shift posts into `app.org_today()`, so that is the day used.
4. **Snapshot fields:** the receipt also needs the SKU (`internalCode`), the product's Arabic name
   (`description`) and the tax class's ETA type and subtype; they are in the snapshot. Still no cost, supplier
   or margin.
5. **Fiscal payload:** T02 stores `payload = {receipt_json}` (the exact text sent). The offline row stores
   the same shape, the text taken from the content with Postgres `json` (number text kept), so T02's submit
   job sends it unchanged.
6. **RLS by organization and branch:** `authenticated` can SELECT the four new tables directly (`offline_sales`
   column-limited, without `content` and `signature`, and only with `offline.resolve`), so each policy also
   checks `app.has_branch_access(branch)` (the device's branch for `device_offline_keys`). For that,
   `app.has_branch_access(uuid)` is granted to `authenticated`, as `app.has_permission` already is; it answers only
   about the caller's own branches. Test: "RLS ..." in `s08_offline_test.sql`.
7. **Idempotency:** `offline_sales` has `UNIQUE (organization_id, idempotency_key)` as well as `(device_id, seq)`
   (TEST-4's ledger registry requires it). The same key with another sequence is refused at receive as
   `KEY_REUSED` (rejected, alert), like `SEQ_REUSED`.
8. **Alerts:** "an alert" is a critical audit row `offline.alert` (code and ids only) written in the transaction,
   plus Q02's `captureProblem` from the API. There is no `captureOperationalAlert` helper on `main`.
9. **QR:** the device computes and prints it; the worker recomputes it with T02's `qrPayload` from the verified
   receipt and stores it on the fiscal row (`qr_payload`), so the shop's reprints come from the server.
10. **Lease ETA readiness:** besides the four fields of D2.4, the seller block the receipt needs (name,
    governorate, city, street) must be complete, or the device could print a receipt T02 can't send.
11. **`fiscal_events.kind`:** T03's events table had no kind; S08's five event kinds need one (see the table).
12. **Web unit tests** use the in-memory `memoryDb()` with the same interface as the IndexedDB wrapper
    (`fake-indexeddb` would be a new dependency). Real IndexedDB, the service worker and Web Locks are covered by
    the e2e run.
13. **E2E and persistent storage:** headless Chromium never grants `navigator.storage.persist()` (Chrome grants it
    from engagement or an installed app). The e2e cashier's browser stubs it as granted; W7 covers "denied".
14. **CSP (D15.4):** two origins beyond the list, so merged features keep working: `img-src` has the Supabase
    origin (S04's shop logo is a signed Storage link) and `connect-src` the Sentry origin when Q02's DSN is set.
    Fonts are emitted as files (never `data:` URLs), so no `font-src` exception is needed.
15. **Service worker registration** uses `immediate: true`: the register module is loaded after the page, when the
    window's `load` event may be gone.
16. **Fake ETA:** one more POS serial (`S08-POS-1`) in `src/test/fake-eta-server.ts` for the e2e device.
