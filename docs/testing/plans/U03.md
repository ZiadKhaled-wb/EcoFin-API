# U03 Supplier payments test plan

**Slice:** U03 · Supplier payments (EC-55). **Decision:** D58. **Done when:** a double-click pays once; invoice and supplier balances update.

## SQL (`supabase/tests/u03_supplier_payments_test.sql`)

```text
npm run db:smoke -- supabase/tests/u03_supplier_payments_test.sql
```

- **Setup:** the main safe holds 50 000.00 (a K01 opening balance); supplier Nile (terms 7 days) has two approved invoices, A = 11 400.00 (10 days old) and B = 5 700.00; supplier Delta has 1 140.00 and 57 000.00.
- **Done when (double click):** 3 000.00 to A with key K → A owed 8 400.00, Nile's balance down 3 000.00, the safe 47 000.00, one `supplier_payment` movement, an SP number, the trimmed reference, one audit row; **K again** → the same payment; the safe, the balances, the movement count and the audit count unchanged.
- **Several invoices:** 10 000.00 with no allocations → oldest first: A 8 400.00 (paid off), B 1 600.00.
- **Overpay:** more than Nile is owed → `PAYMENT_EXCEEDS_OUTSTANDING` with the outstanding; an allocation above its invoice → the same code with that invoice; a paid-off invoice → `outstanding: 0.00`.
- **Allocations:** not adding up, another supplier's invoice, a draft invoice, the same invoice twice, an empty list, an amount of 0, an unknown key → `ALLOCATION_INVALID`. Amount 0, three decimals, a `system:` key, a reference over 100 characters → `VALIDATION_FAILED`; an unknown supplier → `SUPPLIER_NOT_FOUND`. Nothing posted by any refused call.
- **Funds and accounts:** more than the safe holds → `INSUFFICIENT_FUNDS`, no payment and no allocation; an inactive safe → `CASH_ACCOUNT_INACTIVE`; another branch's or another shop's safe → `VAULT_INVALID`; an empty shop-wide bank can't go below 0; a funded shop-wide bank pays, booked in the payment's branch.
- **Credit return interplay:** after a U04 credit return on B, B's outstanding and the cap include it.
- **Open invoices:** only what is still owed, oldest first, with paid, returned credit, the due date from the supplier's terms and the overdue flag; the total outstanding.
- **Reversal:** the owner reverses the 3 000.00 payment → the safe +3 000.00 (a movement linked to the original), A owed 3 000.00 again, Nile's balance back up, its own SP number, linked both ways, audited as a warning with the reason; the same key → the same reversal; a new key → `PAYMENT_ALREADY_REVERSED`; reversing the reversal and a short reason → `VALIDATION_FAILED`; the key of another payment → `IDEMPOTENCY_CONFLICT`; an unknown payment → `SUPPLIER_PAYMENT_NOT_FOUND`.
- **Statement and list:** the U01 statement shows the payments and the reversal and closes at `v_supplier_balances.balance`; the list is newest first, filters by supplier, branch and dates, pages, and without reversals shows only the payments that count.
- **Roles:** an ACCOUNTANT pays but can't reverse (`APPROVAL_OWNER_ONLY`); a WAREHOUSE user can't pay or list open invoices (`PERMISSION_DENIED`) but reads payments; another branch's manager can't pay from main (`BRANCH_DENIED`), can't reverse, doesn't see main's payments or open invoices.
- **Tenancy, ledger, expired shop, grants:** shop B gets not found for a's supplier, payment, reversal and open invoices; no direct writes to `supplier_payments`; `app.ledger_mismatches()` is empty and the safe adds up; an expired shop reads but can't pay or reverse; the five functions are granted, the helper isn't.
- **Other suites:** `ledger_invariants_test.sql` (replay list: `post_supplier_payment`, `reverse_supplier_payment`), `tenant_and_permission_test.sql` (denial cases for the five functions, run before U04's return uses up the invoice), `security_guards_test.sql` (the three reads allowlisted).

- `src/services/supplierPayments.service.test.ts`: RPC arguments (reference and allocations only when given, filters and paging), `PAYMENT_EXCEEDS_OUTSTANDING` mapped with its details, `INSUFFICIENT_FUNDS`, a malformed row refused.
- `src/routes/supplierPayments.integration.test.ts` (local stack): a missing key is 400; **two parallel POSTs with one key → one payment, the same body**, the safe, the invoice and the supplier balance change once; the rest of the invoice paid with no allocations → outstanding 0.00; the open invoices; above what is owed → 409 with the outstanding; the owner reverses (the safe and the balances go back; again → `PAYMENT_ALREADY_REVERSED`); the list with and without reversals; an accountant pays but gets 403 `APPROVAL_OWNER_ONLY` on a reversal.
