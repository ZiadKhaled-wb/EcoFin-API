# T03 ETA submission monitor and corrections test plan

**Slice:** T03 · ETA monitor and corrections (EC-91). **Spec:** [`docs/eta/ERECEIPT_SPEC.md`](../../eta/ERECEIPT_SPEC.md) section 13a.
**Done when:** (1) a rejected receipt shows the ETA's reason and, after the fix, is resent as a corrected receipt (new UUID with `referenceOldUUID`) and accepted by the fake ETA; (2) a blocked receipt becomes prepared after its data is fixed.

| Done when | Proven by | Status |
| --- | --- | --- |
| (1) rejected, reason shown, corrected and accepted | T03-I-001 | passing (local) |
| (2) blocked, then prepared after the fix | T03-I-002 (and T03-I-003 for a receipt without a POS) | passing (local) |

One row per test. 20 unit, 6 contracts, 125 SQL, 9 integration (plus 5 audit drivers and 9 cross-shop cases in the shared suites). Web: `EcoFin-Web/docs/testing/plans/T03-web.md`.

## What T02's loaders did (decisions 5 and 8)

- **Prepare loader** (`eta_load_pending_for_device`): takes every `pending` row **without a UUID** whose `fiscal_submissions.device_id` is the POS (or, for `p_device_id` NULL, the branch's rows without a POS). It already read the device from the **fiscal row** and joined `devices` on `f.device_id`, never `sales.device_id`: no change was needed. After `fiscal_assign_device` sets `fiscal_submissions.device_id` the next `eta.prepare` of that POS takes the row.
- **Submit loader** (`eta_claim_for_submit`): takes **every** `pending` row of the POS that has a UUID and is due (`next_retry_at` null or past), in issue order. It does not look at the chain head, so a corrected receipt that is not the newest is sent: no change was needed.

## Replaced T02 functions

| Function | Why |
| --- | --- |
| `public.retry_fiscal_submission(uuid)` | `CREATE OR REPLACE` with T02's body copied; one added check at the start of the status checks: a `rejected` row raises `USE_CORRECTION` (decision 1). |

No T02 loader was replaced. `public.eta_enqueue` (service-role wrapper) was not changed: `eta.correct` is queued only by `public.fiscal_request_correction`, inside the database.

## Where the task file was not followed to the letter

- **`send_failed`:** T02 never writes `failed` with a UUID (a failed send stays `pending` with the error and a retry time). The situation exists and is classified, but no T02 path produces it today. A `failed` row without a UUID that does not start with `BLOCKED:` is shown as `blocked`.
- **Deadline of a row at the ETA:** a `submitted` row has no deadline (nothing is left to submit).
- **`fiscal_assign_device`** re-queues the row itself and writes one audit row (`fiscal.device_assigned`), instead of calling `retry_fiscal_submission` (which would write a second one).
- **`fiscal_day_summary.all_accepted`** is true when nothing is waiting or in trouble: a void's `cancelled` receipt does not count against it, and a day without receipts is true.
- **List answer:** `fiscal_list` returns a JSON array of rows (each with `total_count`); the API answers `{ items, total_count }`. Rows also carry `sale_id` for the link to S07's sale page.
- **The ETA error** is parsed in the API (`src/eta/correct.ts`), not in SQL: the database returns the stored text.
