# U05 Purchase orders test plan

**Slice:** U05 · Purchase orders (EC-57). **Decision:** D59. **Done when:** receiving part of an order leaves the rest open; a special customer order shows its purchase order status.

## SQL (`supabase/tests/u05_purchase_orders_test.sql`)

```text
npm run db:smoke -- supabase/tests/u05_purchase_orders_test.sql
```

- **Draft:** an order of 9 TVs + 5 cables is created as a draft numbered PO, audited once; the same key → the same order; a draft takes a date, notes and new lines (10 TVs), audited once, and no change writes nothing; an unknown key, the same product twice, quantity 0, a cost with three decimals, no lines and an unknown product are refused. Send: draft → sent, audited; twice → unchanged.
- **Done when (partial receipt):** an invoice from the order for 6 TVs + 5 cables is a draft with the order's supplier, the expected costs and linked lines (the same key → the same invoice); a draft does not count as received and shows on the order as on draft invoices; approved → `partially_received`, TV 4 and cable 0 still to come, stock up by 6 and 5 only, the order's detail shows it and its invoice.
- **The rest:** with no lines given the invoice takes the 4 TVs still to come; approved → `received`; a third invoice → `PO_CLOSED`; cancelling a received order → `PURCHASE_ORDER_NOT_EDITABLE`.
- **Over-receipt:** on a fresh order with 4 still to come, invoicing 5 → `PO_OVER_RECEIPT` with `remaining: 4`; editing a draft above it → the same; two drafts of 4 each: the first approves, the second approval → `PO_OVER_RECEIPT` with 0 and nothing posted.
- **States:** invoicing a draft order → `PO_NOT_SENT`; editing a sent order → `PURCHASE_ORDER_NOT_EDITABLE`; a partly received order cancels with a reason (required), audited once as a warning; then invoicing and approving an earlier draft → `PO_CLOSED`; cancel twice and sending a cancelled order are refused; a draft can be cancelled.
- **Mismatch (U02's create with an order):** a linked line of another product, another supplier, another branch, an order line without the order, a line of another order → `PO_LINE_MISMATCH`; an unknown order → `PURCHASE_ORDER_NOT_FOUND`. An invoice of the order may carry an extra line without the link, which does not count as received. An invoice without an order has null order fields.
- **Done when (special order):** with an open customer order (inserted directly; S10 comes later), a PO line with its `sales_order_line_id` makes the customer's line point to it; the order's detail names the customer order; `app.sales_order_line_po_status` shows the order as draft, then `partially_received` after a partial approved invoice; a from-stock line, an already linked line, another product and an unknown line → `SALES_ORDER_LINE_INVALID`; replacing a draft's lines keeps the link.
- **List:** every order with its counts (lines, ordered, received); filters by status, supplier, branch and number; paging; an unknown status refused.
- **Roles:** a WAREHOUSE user creates, sends and receives an order but can't approve; a CASHIER can't list, read or create; another branch's manager gets not found for main's orders (read, send, receive), can't order for main (`BRANCH_DENIED`) and lists none.
- **Tenancy, ledger, expired shop, grants:** shop B gets not found for a's order (read, receive, cancel) and supplier; no direct writes to `purchase_orders`; `app.ledger_mismatches()` is empty; an expired shop reads but can't order or receive; the eight functions are granted, the helpers aren't.
- **Other suites:** `u02_purchase_invoices_test.sql` and `u06_purchase_approval_test.sql` pass (U02 only updates the `create_purchase_invoice` signature in its grants check); `ledger_invariants_test.sql` (replay list: `create_purchase_order`, `create_invoice_from_po`), `tenant_and_permission_test.sql` (denial cases for the seven functions), `security_guards_test.sql` (the two reads allowlisted).

## Contracts and API

- `packages/contracts/src/purchaseOrders.test.ts`: the create body (each product once, quantity 1-100 000, optional non-negative cost, trimmed notes, strict), update needs a key, cancel needs a reason, the list query, the receive body (no lines, or order lines once each), U02's create with an order, the order, the details and the error codes.
- `src/services/purchases.service.test.ts` (U05 block): RPC arguments (optional keys left out, null clears, filters and paging, receive with and without lines, U02's create passes the order), `PO_OVER_RECEIPT` mapped with its details, an invoice without an order reads null order fields.
- `src/routes/purchaseOrders.integration.test.ts` (local stack): a missing key is 400; the owner creates an order (the same key → the same order), edits it, can't receive a draft (`PO_NOT_SENT`), sends it, can't edit it, receives 6 TVs + 5 cables as a draft invoice (the same key → the same invoice; on draft invoices 6), approves it → `partially_received` and stock 6 and 5; 5 more TVs → 409 `PO_OVER_RECEIPT` with `remaining: 4`; the rest with no lines → 4 TVs, approved → `received`; again → `PO_CLOSED`; the list by status and number. A warehouse user orders, sends, receives and cancels (a reason is required) but gets 403 on approve.
- Cross-shop (139 routes): the 7 routes refuse a foreign header and an org id; shop B's supplier, branch, product and order are refused, an unknown customer order line is refused, and B's order is left unchanged with no invoice. Audit drivers for the 5 writes (`purchase_order.created`, `.updated`, `.sent`, `.cancelled`, and `purchase_invoice.created` for Receive).
