# N03 Collections test plan

**Slice:** N03 · Collections (installment payments) (EC-82). **Decision:** D78. **Rules:** `docs/ISLAMIC_FINANCE_RULES.md` (rule 4: no late fees at all). **Done when:** allocation is the same every time for the same inputs; a double-click records one payment; the last payment closes the contract; a same-day reversal leaves the contract as it was.

## SQL (`supabase/tests/n03_collections_test.sql`)

```text
npm run db:smoke -- supabase/tests/n03_collections_test.sql
```

Shops a (retail_pro) and b (retail). In shop a: an owner, a cashier with an open shift in the main branch, a cashier with an open shift in a second branch, a warehouse user, a branch manager without a shift, a cashier without `collection.create` (override) and a cashier given `collection.reverse` (override). Six real N02 contracts (12 000.00, 2 000.00 down, 12 monthly lines of 1 000.00 at 20 %): two for one customer, one for another, two for the reversal customer, one in the second branch.

- **Allocation:** the preview of 2 500.00 pays lines 1-2 and 500.00 of line 3, its profit first; the same state and amount give identical rows twice; above the remaining → `exceeds_remaining`, no lines.
- **Collect:** 1 000.00 cash pays line 1 exactly (profit and principal); one payment row that is its own receipt (`collection_id = id`) with the request key; the drawer +1 000.00 (one `collection` movement on the shift); the answer and the `collection.created` audit row. The same key again → the same receipt, nothing written. 2 500.00 then pays lines 2-3 and 500.00 of line 4.
- **Split and several contracts:** 600.00 cash (tendered 700.00) + 400.00 bank → two rows under one receipt, the second with the system key; allocations spread over both rows, each balanced; change 100.00. One collection of 1 000.00 + 500.00 on two contracts paid 1 200.00 cash + 300.00 bank.
- **Refusals (nothing written, no number taken):** one cent above what is left → `COLLECTION_EXCEEDS_REMAINING {contract_id, remaining}` (nothing for the first contract either); another customer's or an unknown contract → `CONTRACT_NOT_FOUND`; a contract twice, store credit, amount 0, three decimals, tendered below the amount, two cash lines, five lines, an unknown field, a system key → `VALIDATION_FAILED`; lines not adding up → `PAYMENT_TOTAL_MISMATCH`; an old `expected_remaining` → `COLLECTION_DUE_CHANGED`; shop B's bank → `VAULT_INVALID`; a sale's key → `IDEMPOTENCY_CONFLICT`; a warehouse user → `PERMISSION_DENIED`; the manager without a shift → `SHIFT_REQUIRED`.
- **No fees (rule 4):** a seeded charge is not in what is left nor in the preview, and is never paid.
- **Any branch:** a main-branch contract paid on a second-branch shift; the payment, the cash movement and the drawer are the second branch's.
- **Completion:** the last payment → `completed`, `closed_at`, every line paid, `contract.completed`, R03 exposure no longer counts it; then `CONTRACT_NOT_OPEN`; the closing key still returns its receipt.
- **Reversal:** the owner's example (two installments paid on the 12th, taken back the same day, then the 12th paid alone): a cashier without the key → `PERMISSION_DENIED`; no reason → `VALIDATION_FAILED`; a non-receipt row → `COLLECTION_NOT_FOUND`; two out rows under one reversal receipt; drawer and bank back; the contract's balance and R03 exposure equal to before; the same key → the same answer, another key → `already_reversed`; an older collection while a later one counts → `not_latest`; a cashier given `collection.reverse` reverses the latest; a completing collection reversed → `active`, `closed_at` NULL, `contract.reopened`; another business day → `not_same_day`.
- **Rescheduled contract:** a seeded version 2 → only its lines are paid.
- **Reads and visibility:** the search by number prefix, name, phone, exact national ID (a prefix finds nothing), status, overdue, customer, cursor; a cashier (collection key) lists and opens a second-branch contract; a user without the collection keys sees only their branch (`get_contract` → `CONTRACT_NOT_FOUND`) and gets `PERMISSION_DENIED` on the preview and the receipt; the receipt with and without a reversal; a sale's payment → `COLLECTION_NOT_FOUND`; the print log (original, then copy); shop B sees nothing of shop A.
- **Permission, expiry, ledgers, grants:** `collection.reverse` exists for OWNER and BRANCH_MANAGER, not CASHIER; an expired shop reads the preview and the receipt but can't collect; cash balances equal their ledgers; no store credit written; the helpers are not executable by `authenticated`, the six public functions are.
- **Other suites:** `tenant_and_permission_test.sql` (denial cases for the six functions, the owner's same calls work), `security_guards_test.sql` (`preview_collection`, `list_contracts`, `get_collection` as reads), `ledger_invariants_test.sql` (`post_collection`, `reverse_collection` replay-tested), `sales_idempotency_test.sql` (both registered), `n02_installment_sale_test.sql` (its other-branch read case now uses a cashier without `collection.create`).

## Concurrency (`npm run db:stock-cash`, rounds L)

- **L1:** 20 requests with one key → one receipt, one payment, one cash movement, 1.00 allocated once.
- **L2:** 20 tills each paying the whole remaining of one contract with `expected_remaining` → one collection, 19 `COLLECTION_DUE_CHANGED` / `CONTRACT_NOT_OPEN`, completed once.
- **L3:** 20 tills paying 1.00 each on one contract → all taken, no line paid beyond its amount, 21 receipts.
- **L4:** 20 two-contract payments, half A then B, half B then A → all taken, no deadlock.
