# S10 sales orders, deposits, reservations (EC-77)

Decisions 5 and 8 can be done on this code. One mismatch on decision 8 (below, §1.4a): S02's
posting step is sale-bound, so only its input parser, its shop checks and the numbering are reusable
as-is. The ledger inserts follow S02's rows, the same way N03 collections already does it.

## 1.4 Findings

**(a) S02 internals for decisions 8 and 9**

- Shape and limits of the payment lines: `app.sale_payments_input(p_payments jsonb) RETURNS TABLE (line_no integer, method text, amount numeric, tendered numeric, cash_account_id uuid, reference text)` (`20261012100000_s02_split_payments.sql:35`). 1-5 lines, at most one cash and one store credit, up to three banks. A bank transfer needs a reference (1-100 chars) and `cash_account_id`. Refuses with `VALIDATION_FAILED`.
- Shop checks: `app.sale_payments_check(p_org uuid, p_branch uuid, p_customer uuid, p_payments jsonb) RETURNS void` (`:105`). The bank must be an active `bank` account of the branch or shop-wide, else `VAULT_INVALID` / `CASH_ACCOUNT_INACTIVE`. Store credit needs the customer.
- Payment numbers: `app.next_document_number(p_organization_id uuid, p_branch_id uuid, p_doc_type public.doc_type)` with `'payment'` (baseline `:2438`).
- Posting: `app.post_sale_payments(p_sale public.sales, p_shift public.shifts, p_emp uuid, p_payments jsonb, p_amount numeric)` (`:130`) is **not callable** for an order. It needs a `sales` row, writes `payment_allocations.sale_id`, and posts `cash_movements.type 'sale'` / `source_type 'sale'`. Precedent: N03 (`20261019090000_n03_collections.sql:300-340`) calls `sale_payments_input` + `sale_payments_check` and writes `payments`, `cash_movements` and allocations itself. S10 adds one internal function, `app.post_order_payments(...)`, that copies S02 `:149-196` row by row:
  - deposit: `direction 'in'`, cash movement `+amount`, `type 'deposit'`;
  - refund: `direction 'out'`, cash movement `-amount`, `type 'refund'`;
  - store credit: the deposit takes `-amount` and locks `store_credit_balances ... FOR UPDATE` as at `:155-164`; the refund puts back `+amount`.
- Shift and device: `app.require_open_shift(p_org uuid, p_emp uuid)` (`20261011160000_k02_shifts.sql:192`), then `SELECT ... FOR UPDATE` and `app.require_shift_device(p_shift_id uuid)` (`20261014210000_ec147_shift_device_check.sql:3`).
- The cash-movement types `deposit` and `refund` both exist (`public.cash_movement_type`, baseline `:170`).

**(b) Decision 5.** `app.check_stock_movement()` is defined only in `20261002000000_v1_baseline.sql:2597`. No later migration replaces it. The outgoing check (`:2622-2628`):

```sql
    IF NEW.quantity < 0 THEN
        -- Out: the unit must be here and available (a reservation is released first).
        IF v_unit.branch_id <> NEW.branch_id OR v_unit.status NOT IN ('in_stock', 'reserved') THEN
            RAISE EXCEPTION 'UNIT_NOT_AVAILABLE: % is % at another or same branch', v_unit.serial, v_unit.status
```

The change: `v_unit.status <> 'in_stock'`, with the same code and message. Flows that already refuse a reserved unit before the trigger runs, so they don't depend on it: the S01 cart (`s01_sale_core_test.sql:306-308` expects `UNIT_NOT_AVAILABLE`), I03 send transfer and I02 adjustment (`i03_transfers_test.sql:193-200`), and the U04 supplier credit (`u04_purchase_returns_test.sql:184-186`). I found no flow that moves a `reserved` unit without releasing it first. S08 `app.offline_process` posts through the same trigger, so an offline sale of a reserved serial is now refused (intended). O16 proves it.

**(c) Line freeze.** `trg_sales_order_lines_final BEFORE INSERT OR UPDATE OR DELETE ... app.freeze_lines_when_parent_status('sales_orders', 'order_id', 'partially_delivered', 'delivered', 'cancelled')` (baseline `:2965-2966`). The condition is `IF v_status = ANY (TG_ARGV[2:])` (`:2805`). The header trigger `trg_sales_orders_final` is `freeze_when_status('delivered', 'cancelled')` on `OLD.status` (`:2941`). An `open` order is not blocked: decisions 6 and 7 can update `fulfilment` / `po_line_id`. No `only_columns_change` trigger exists on `sales_order_lines`. **No trigger change is needed.**

**Other mismatches to know**

- U05 `app.set_purchase_order_lines` already accepts `sales_order_line_id` on PO lines (`20261011150000_u05_purchase_orders.sql:90,148`). Read `:140-168` before decision 6: a PO created with it may link the order line without decision 6's checks or audit.
- `REASON_REQUIRED` already exists as 400 (`packages/contracts/src/errors.ts:69`); the spec table says 422. Reuse 400.
- `PO_NOT_FOUND` is not in the spec's code table. Only `PURCHASE_ORDER_NOT_FOUND` (404) exists. S10 adds `PO_NOT_FOUND` 404.
- There is no parallel-session helper in `supabase/tests/helpers/`. O13 uses the row lock plus two sequential calls.
