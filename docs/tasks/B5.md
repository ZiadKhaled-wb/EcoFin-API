## Behaviour
1. Error handler: `AppError` → its status + `{ error: { code, message, details?, requestId } }`. Zod errors → 400 `VALIDATION_FAILED` with field issues in `details`. Postgres/Supabase errors whose message starts with a contract code (e.g. `OUT_OF_STOCK`, `PERMISSION_DENIED`, `DAY_CLOSED: …`) → that code + `errorCodeHttpStatus[code]`, with a **safe** message (never the raw DB text, hint or detail). Add `mapDbError(err)` in `src/utils/errors.ts` for this; F04+ will reuse it. Anything unknown → 500 `INTERNAL`, generic message; the real error is only logged.
2. Request id: take `x-request-id` if it's a safe token (≤ 128 chars, `[A-Za-z0-9._-]`), else generate a UUID; echo it in the response header; put it on the logger child and in error bodies.
3. Logger: pino; redact `password`, `newPassword`, `token`, `accessToken`, `refreshToken`, `authorization`, `cookie`, `national_id`, `nationalId`, `apikey`, at any nesting depth used in request logging (headers, body). Test it.
4. Env: `loadEnv(source = process.env)` returns the parsed env or throws one error that lists **every** bad or missing variable by name (never their values). Called on startup in `server.ts` / `worker.ts`, **not** at import time, so tests can import modules freely. Keep the existing variable names; add `CORS_ALLOWED_ORIGINS` (comma-separated, required in production), `TRUST_PROXY` (number of hops or `false`, default `1`), `LOG_LEVEL`.
5. Health: `GET /health` runs a cheap DB check through the server Supabase client with a short timeout. Ok → 200 `{status:'ok', db:'ok'}`; DB down → 503 `{status:'degraded', db:'down'}`. Mock the client in unit tests.
6. Rate limit: `app.set('trust proxy', env.TRUST_PROXY)`; keep the existing limiter, keyed by client IP as Express resolves it behind the proxy. A test proves two different `X-Forwarded-For` clients get separate buckets **only** when trust proxy is on.
7. helmet with defaults suitable for a JSON API; CORS: only origins in the allow-list, credentials as today, no `*`.
