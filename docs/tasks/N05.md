## Goal
Three controlled changes to an open installment contract, each made in one transaction, each leaving a `contract_changes` row and an audit row, **none editing or deleting anything that exists**:
- **Early settlement:** the customer pays everything left today. The screen shows the payoff (what is left on the current schedule) and the policy's **suggested** waiver; a manager may waive part of the remaining profit with a reason (rule 6). The payment goes through N03's collection machinery (receipt, drawer, bank lines); the contract closes.
- **Rescheduling:** what is left (principal and profit, **exactly**: rule 5) is spread over a new schedule (count, frequency, first due date). The old schedule stays, marked superseded and linked to the change.
- **Write-off:** the owner marks what is left as lost, with a reason. The contract closes as `written_off`; the amount shows in the change list (reports read it).

## Decisions (record them in D80)
1. **Everything is a new linked record.** `contract_changes` (baseline table, unused until now) gets one row per change: `kind`, `old_version`, `new_version` (reschedule and settlement), `amount` (payoff / rescheduled / written-off amount), `profit_waived`, `reason`, `approved_by` (the caller for a waiver or write-off), `idempotency_key`. Add columns: `branch_id` (the contract's, for reports by branch), `principal_amount`, `profit_amount` (the split of `amount` before any waiver), `payment_id` (settlement: the collection's receipt, FK to `payments`), `business_date` (shop date). Old schedule lines only get `superseded = true` (the one column the frozen trigger allows); contracts only change `status`, `current_version`, `closed_at` (allowed by `trg_contracts_frozen`). Nothing else is updated. RLS: select for the shop's employees through the functions only (like N03 / N04); no direct writes. Index `(organization_id, kind, business_date)`.
2. **No new contract status.** Settlement ends in `completed` (the change row says it was an early settlement); reschedule in `rescheduled`; write-off in `written_off` (all three exist in `contract_status`). No enum value is added, so an older Web build keeps parsing contracts. The three permission keys already exist in the baseline (`contract.settle_early`, `schedule.change`, `contract.write_off`), so no new key either; check the Web's `PermissionKey` enum already lists them (it is generated from contracts) and say so.
3. **The new-version trick (one mechanism for settlement and reschedule).** A change that alters what is left writes **schedule version `current_version + 1`** and supersedes every line of the current version. The new version's lines carry exactly what was left: per line, `principal` and `profit` from the old version's **remaining** principal and profit (effective allocations only). Payments already made stay on the superseded lines, so D74's formula (contract total = current lines + paid on superseded lines) and `v_contract_balances` (paid over every version, remaining over the current one) stay correct with no view change. Collections already use `current_version`, so N03 keeps working unchanged after a reschedule.
4. **Version check (replaces the `TODO(N05)`).** Extend `app.schedule_lines_sum_check` for `version > 1`: the new version's lines run 1..n without a gap, and their `sum(principal)`, `sum(profit)` equal the change row's `principal_amount` and `profit_amount − profit_waived` (for a reschedule `profit_waived` is 0). A version > 1 without a matching `contract_changes` row is refused (`SCHEDULE_NOT_BALANCED`). This is the database safety net for rule 5: a reschedule can never add to the total.
5. **Early settlement** (`contract.settle_early`; BRANCH_MANAGER by default, OWNER always):
   - **Payoff** = the contract's remaining on its current version (`app.contract_remaining`), split into `principal_left` and `profit_left`.
   - **Suggested waiver** from the contract's **own** policy version (`contracts.policy_id`): `no_discount` → 0; `waive_future_profit` → the remaining profit of the lines **not yet due** (`due_date > today`); `percent_of_future_profit` → `early_settlement_pct` % of that, rounded down to the piaster. Shown as a suggestion only (rule 6).
   - **Waiver** in the request: 0 ≤ waiver ≤ remaining profit of the not-yet-due lines (**max waiver**; overdue and due-today profit is owed in full), else `WAIVER_TOO_HIGH` (422, `{max_waiver}`). Waiver > 0 needs a `reason` (3-300); a waiver different from the suggestion is allowed (the manager decides).
   - **The write:** lock the contract; check `expected_remaining` (else N03's `COLLECTION_DUE_CHANGED`); insert the change row (`early_settlement`, `amount` = payoff, `profit_waived`); supersede the current lines; insert version + 1 = **one line** due today with `principal = principal_left`, `profit = profit_left − waiver`; call `app.post_collection_core` with that contract and amount = payoff − waiver and the request's payment lines (cash to the caller's open shift drawer, bank lines as S02). The core completes the contract (remaining 0) and writes `collection.created` + `contract.completed`; this function adds `contract.settled_early` (severity `warning` when waiver > 0, else `info`) and stores the receipt in `contract_changes.payment_id`.
   - **Reversal:** a settlement's collection **cannot** be reversed with N03's reverse (`SETTLEMENT_NOT_REVERSIBLE`, 409): it would reopen a one-line version with the waiver in it. A wrong settlement is an owner's correction (out of scope; see "To confirm").
   - Needs the caller's open shift like a collection (N03's shift errors, e.g. `SHIFT_CLOSED`); the contract may belong to any branch (N03's rule); module `installments`; not in an expired shop.
6. **Rescheduling** (`schedule.change`; BRANCH_MANAGER by default, OWNER always):
   - Input: `installments_count` (1-520), `frequency` (one of the contract's policy `allowed_frequencies`), `first_due_date` (today + 1 to today + 60, N01's range), `reason` (3-300, required), `expected_remaining`.
   - The lines: the remaining **total** spread with N01's `app.installment_regular` and the policy's `rounding_step` (last line takes the rest), profit spread in proportion to the amounts, largest remainder in piasters (the same code as `app.installment_terms`: extract it into `app.schedule_split(p_principal, p_profit, p_count, p_frequency, p_first, p_step)` and make N01 call it, so the two can't drift; N01's tests must stay green). Total, principal and profit equal what was left (decision 4).
   - **No policy limit checks** beyond frequency, count and the first-date range: the term limits (`max_months`, `min_installment`) guarded the original price; a reschedule doesn't change the price. `INSTALLMENT_TERMS_INVALID` for a bad count / frequency / date with the same `violations` shape as N01.
   - The write: lock; `expected_remaining`; change row (`reschedule`, `amount` = remaining, `new_version`); supersede; insert the new lines; contract `status = 'rescheduled'`, `current_version + 1`; audit `contract.rescheduled` (severity `warning`, old and new line counts, first/last due dates).
   - Allowed on `active` and `rescheduled` contracts with remaining > 0 (several reschedules are fine, each a new version). The customer's ban (N04) does not block a reschedule (it helps them pay).
   - **N04 interplay:** the new lines have new ids, so N04's ban and legal keys (per line) start fresh; an **open legal referral stays open** (it is the owner's to dismiss); open warnings become `resolved` on the next run when nothing is overdue. Say so in D80.
7. **Write-off** (OWNER only: `app.current_role() = 'OWNER'` as N04's dismiss; the `contract.write_off` key stays for the role matrix, see "To confirm"):
   - Input: `reason` (3-300, required), `expected_remaining`.
   - The write: lock; `expected_remaining`; change row (`write_off`, `amount` = remaining, `principal_amount`, `profit_amount`, `approved_by` = caller); contract `status = 'written_off'`, `closed_at = now()`; **no new version, nothing superseded** (the lines show what was lost; `v_schedule_line_status` already reports them `closed`); audit `contract.written_off` (severity `critical`).
   - After a write-off no collection, settlement or reschedule is possible (`CONTRACT_NOT_OPEN`, already N03's rule). Recovering money later is out of scope.
   - The customer's status is not changed automatically (the owner can block by hand, R01).
8. **Collections reversal guard.** Recreate `public.reverse_collection` with one extra check: refuse when any contract it paid has a `contract_changes` row created **after** the collection (`CONTRACT_CHANGED_SINCE`, 409, `{contract_id, change_id}`): reversing would un-pay superseded lines that the new version no longer carries. Plus decision 5's `SETTLEMENT_NOT_REVERSIBLE`. All other checks unchanged.
9. **Idempotency:** the three writes take an `Idempotency-Key` header like N03; the same key returns the first answer; a key used by another change, payment or sale → `IDEMPOTENCY_CONFLICT`. Settlement's payment rows use the key as N03 does (`system:settlement:<change id>:<n>` for rows after the first).
10. **Visibility:** N03's `app.can_see_contract` (collection keys see every branch). Extend it with `schedule.change` and `contract.settle_early` (one helper, say so in D80); write-off is owner-only and the owner sees everything.
11. **Who sees the changes (reports):** `GET /api/contract-changes` for `report.financial` holders and the three change keys; it is the data D0x reports read for write-offs and waived profit. No figure is called "interest" or "discount promised" anywhere (rule 3, rule 6): the waiver is labelled **"profit waived at settlement"** (Arabic **تنازل عن جزء من الربح عند السداد المبكر**).

## Done when
- **Balances right after each action** (SQL test, one contract through each path): R02's account (`get_customer_account`) and `v_contract_balances` give: after a reschedule the same `remaining` as before and the same contract total; after a settlement `remaining = 0`, `paid` = earlier payments + payoff − waiver, contract total = `total_payable − profit_waived`; after a write-off the contract leaves the open balance and the change row holds the old remaining.
- **Old schedule visible:** after two reschedules, route 6 returns 3 versions, the first two superseded and linked to their change rows; no `schedule_lines` row was updated except `superseded`, no row deleted (count before ≥ count after per version).
- **Rule 5 safety net:** a direct insert of a version > 1 whose sums don't match its change row (or with no change row) is refused `SCHEDULE_NOT_BALANCED`.
- **Waiver:** `percent_of_future_profit` 50 → suggestion = half of the not-yet-due profit; waiver above the max → `WAIVER_TOO_HIGH`, nothing written; waiver 0 needs no reason; waiver > 0 without reason → `VALIDATION_FAILED`.
- **Idempotent:** the same key twice → one change row, one collection; a stale `expected_remaining` → `COLLECTION_DUE_CHANGED`.
- **Collections after a reschedule** allocate to the new lines oldest first; the last one completes the contract.
- **Reversal guard:** collection then reschedule same day → reversing the collection is `CONTRACT_CHANGED_SINCE`; reversing a settlement's collection → `SETTLEMENT_NOT_REVERSIBLE`.
- **N04:** an overdue contract rescheduled → next overdue run resolves its warnings when nothing is late; an open legal referral stays open.
- **Access and isolation:** cashier → `PERMISSION_DENIED` on settle / reschedule; branch manager → `PERMISSION_DENIED` on write-off; shop B's contract id → `CONTRACT_NOT_FOUND`; an expired shop can read quotes and history but not write.
- All local checks green (unit, contracts, SQL files, integration, Web unit + e2e), as in N04.

## To confirm (defaults used unless the owner says otherwise)
- **Max waiver** = remaining profit of the lines not yet due (overdue and due-today profit is owed in full). Alternative: any part of the remaining profit.
- **Write-off by the owner only.** Alternative: anyone holding `contract.write_off` (the owner could grant it to a branch manager).
- **A reschedule keeps the profit exactly** (no profit waiver inside a reschedule; a waiver only happens at early settlement). Alternative: allow a manager's waiver during a reschedule too (rule 5 allows a lower total).
- **Reschedule limits:** only count, frequency and first due date (today + 1 to + 60) are checked, not the policy's `max_months` / `min_installment`.
- A wrong settlement can't be reversed in N05 (owner correction later).
