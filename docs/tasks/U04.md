## Goal
A manager sends goods back to a supplier against an approved purchase invoice:
- they pick the invoice, the lines and quantities, and the exact serials for serialized products;
- the goods leave stock **once**, at the invoice's real unit cost;
- what the shop owes the supplier goes down (supplier credit), **or** the supplier refunds cash into a vault;
- the return is numbered;
- nobody can return more than was bought.

## Slice text (U04)
- **Includes:**
  - pick the original invoice and lines (serials for serialized products);
  - quantity ≤ what was bought minus what was already returned;
  - the real unit cost from the invoice;
  - stock out once;
  - supplier balance reduced, or refund recorded to a vault;
  - numbered.
- **Done when:** stock and supplier balance each change exactly once; you can't return more than you bought.

## Decisions already made (record them in D57)
1. **User decision: the average cost is recomputed.** For each product, with the total on hand `Q` (every branch and state) and the average `A` **before** the return, returning `r` units at the invoice's net unit cost `c`:
   - if `Q − r > 0`: `new = (Q×A − r×c) / (Q − r)`, rounded half-up to 4 decimals, and **never below 0** (clamp, and note it in the audit);
   - if `Q − r ≤ 0`: keep `A`.
2. **Refund modes** (baseline enum `purchase_refund_mode`):
   - `supplier_credit` lowers the supplier balance (baseline views). It is allowed even when the invoice is fully paid: the supplier balance may go negative, meaning the supplier owes the shop.
   - `cash`: the supplier pays back. Insert a `cash_movements` row: `+total`, type `supplier_refund`, source `purchase_return`, into an **active** `safe` or `bank` cash account. The account must be in the return's branch, or an org-wide bank with `branch_id NULL` (`VAULT_INVALID` / `CASH_ACCOUNT_INACTIVE`). A cash return does **not** change the supplier balance.
3. **The return is made from the invoice's branch.** The stock must be there: otherwise the ledger trigger refuses with `OUT_OF_STOCK`, or `UNIT_NOT_AVAILABLE` for a serial. Goods moved to another branch must be transferred back first (I03).
4. **Serialized lines return specific units:**
   - the units this invoice line created (`units.purchase_invoice_line_id`);
   - status `in_stock` (a reserved unit is refused, as in I03: `UNIT_NOT_AVAILABLE`);
   - one return line per unit (`unit_id`, quantity 1).
5. **Quantities and tax:**
   - **Returnable** = invoice line quantity − all earlier returned quantities of that line → else `RETURN_QTY_EXCEEDED` (details `{ invoice_line_id, returnable }`).
   - Tax and gross per return line come from `app.return_line_tax` (D41), so all the returns of a line add back to it exactly.
   - `subtotal` = Σ net, `tax_total` = Σ tax, `total` = Σ gross.
6. **The invoice must be `approved`** (`PURCHASE_INVOICE_NOT_APPROVED`). A **reason** is required (3–500). The business date is today's shop date.
7. **Idempotent:** the same key again returns the first return; no second stock or cash movement.
8. **The accounts list** (also for U03): a read `GET /api/purchasing/cash-accounts?branch_id=` lists the active `safe` and `bank` accounts usable for that branch, with balances. It's readable with `purchase.return_create` **or** `supplier.payment_create`. K01 later adds full vault management; this read stays.

## Database facts (baseline; don't alter)
- `purchase_returns`:
  - Columns: `number` (prefix PR), `purchase_invoice_id`, `supplier_id`, `branch_id`, `refund_mode`, `cash_account_id`, `subtotal`, `tax_total`, `total`, `reason NOT NULL`, `business_date`, `idempotency_key`.
  - CHECKs: `(refund_mode='cash') = (cash_account_id IS NOT NULL)`; `total = subtotal + tax_total`. Append-only.
- `purchase_return_lines`: `return_id`, `invoice_line_id`, `product_id`, `unit_id`, `quantity`, `unit_cost`, `tax_amount`, `line_total`; `CHECK (unit_id IS NULL OR quantity = 1)`.
- Stock: `stock_movements` type `purchase_return_out`, **negative** quantity, `unit_cost` = the invoice's net unit cost, source `purchase_return`, `source_line_id` = the return line. For a serial, include `unit_id`: the trigger checks the unit is in that branch and sets it to `returned`.
- Cash: `cash_movements` (`cash_account_id`, `branch_id` = the account's branch or the return's branch for an org-wide bank, `amount > 0`, `type 'supplier_refund'`, `source_type 'purchase_return'`, `source_id`, `business_date`). The `cash_balances` trigger owns the balance.
- `cash_accounts` (`kind` safe | bank | drawer | collector_wallet, `branch_id`, `is_active`, `archived_at`); `cash_balances.balance`. Every shop has a main safe from P01.
- `app.return_line_tax(p_qty, p_tax, p_gross, p_prev_qty, p_prev_tax, p_prev_gross, p_return_qty)`: read its body for the output keys.
- `app.stock_source_json` already names `purchase_return` sources (number and supplier).
- Permission: `purchase.return_create` (BRANCH_MANAGER; OWNER).

## Part A: server + contracts

2. `public.post_purchase_return(p_invoice_id, p_refund_mode, p_cash_account_id, p_reason, p_lines jsonb, p_idempotency_key)`, `purchase.return_create`:
   1. Lock the idempotency key; the same key → the first return.
   2. Lock the invoice: it must be the shop's (`PURCHASE_INVOICE_NOT_FOUND`) and approved (decision 6). The caller needs its branch.
