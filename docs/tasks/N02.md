## Goal
A cashier with an open shift sells goods on installments in **one request**. In one database transaction the server prices the cart (S01/S03), takes the stock, writes the sale with its tax snapshot, takes the **down payment** into the drawer (S02 payment lines), recalculates the terms with the N01 engine from the sale total, checks the customer (national ID, status, credit limit or an approved exception, guarantors, survey), writes the contract with its number and its version-1 schedule, attaches the guarantors, marks the credit exception used and writes the audit rows. A retried request returns the same sale and contract. The contract is never edited afterwards and shows on the customer account (R02).

## Slice text (N02)
- **Includes:** uses the sale core (S01): goods, tax and down payment in the same transaction; contract: number, customer, guarantors, creditor (from P04), cash price, down payment, financed amount, markup, total payable, schedule, policy version used; schedule dates in the shop timezone, month-end dates handled correctly; the contract is never edited (changes go through N05); contract statuses: active → completed / rescheduled / written off / returned.
- **Done when:** the contract total = cash price − down payment + markup; the down payment is in the drawer; the contract shows on the customer account (R02).

## Decisions (record them in D77; the ones marked *to confirm* are defaults: post them on EC-81 before Part B)
1. **Who and where:** `installment.create` (`app.require_permission`, so an expired, read-only shop is refused) **and** `sale.create` (the sale is a sale), module `installments` **and** `pos`, the shop's `installments_enabled` checked early (`INSTALLMENTS_DISABLED`, before any lock; P04's trigger stays the last line). The sale belongs to the caller's open shift (`app.require_open_shift`, locked `FOR UPDATE` as in `post_sale`) and its still-paired device (`app.require_shift_device(shift_id)`, EC-147: `DEVICE_REVOKED` / `DEVICE_MISMATCH`), `app.require_branch_access(shift branch)`; the shift's branch is the contract's branch.
2. **One request, one transaction:** `public.post_installment_sale(p_body jsonb, p_idempotency_key text) RETURNS jsonb`. Body (strict, see the contract): the S03 cart (`lines`, `sale_discount?`, `discount_reason?`, `discount_approval_id?`), `expected_total` (the cash total the cashier saw), `customer_id` (**required**), `terms` = `{ down_payment, installments_count, frequency, first_due_date?, policy_version }` (N01's input without `cash_price` + the version the preview showed), `payments?` (the down payment's S02 lines), `guarantor_ids` (0-3, unique), `credit_approval_id?`.
3. **The cash price is the sale total.** `cash_price` = the sale's `total` after S03 discounts, VAT included as the sale stores it (the price the customer would pay in cash today). The cart is priced by the server exactly as `post_sale` does; `expected_total` ≠ the server total → `PRICE_CHANGED`. **`products.installment_price` is not used** in V1: the only installment price is the N01 engine's (cash price + the policy's profit), so the customer sees one cash price and one installment price per sale (Islamic finance rule 1). *To confirm*: drop or repurpose the column later.
4. **Terms from the engine, never from the client:** call `app.check_installment_terms(org, {cash_price: <sale total>, down_payment, installments_count, frequency, first_due_date}, policy_version)`; its answer (`POLICY_NOT_SET`, `POLICY_CHANGED {current_version}`, `INSTALLMENT_TERMS_INVALID {violations}`, or the terms) is final. The contract's `policy_id`, `markup_pct`, `markup_amount`, `total_payable`, `first_due_date` and the version-1 `schedule_lines` (seq, due date, principal, profit) are copied **from that answer**, nothing recomputed in plpgsql. N01's commit-time trigger re-checks them anyway.
5. **Customer rules, in this order (before any stock lock, so a refused sale changes nothing):**
   - the shop's customer (`CUSTOMER_NOT_FOUND`), not blocked or archived (`CUSTOMER_BLOCKED`);
   - has a national ID → else new `CUSTOMER_NATIONAL_ID_REQUIRED` (409) (D63: "a must for installments"; the POS sends the cashier to the customer form);
   - credit: `app.check_customer_credit(org, customer, financed, credit_approval_id)` (locks the customer row, so two tills can't both use the same available credit; raises `CREDIT_LIMIT_EXCEEDED` / `CREDIT_APPROVAL_REQUIRED` / `CREDIT_APPROVAL_INVALID` as R03 defines);
   - guarantors: `app.check_contract_guarantors(org, customer, policy, financed, guarantor_ids)` (R04's errors, `GUARANTOR_REQUIRED {required, given}`);
   - survey: `app.check_contract_survey(org, customer, policy, financed)` (`SURVEY_REQUIRED {…}`).
   Call the functions; don't copy their logic. Use the exact signatures on `main` (read them, the list above names the arguments, not their order).
6. **Order inside the function** (one transaction): body shape → permission, modules, switch → idempotency lock (a repeat returns the first answer, changes nothing) → shift lock → customer rules 5a-5b → price the cart (S03's `app.sale_cart` path, same validation) and compare `expected_total` → engine (decision 4) → credit, guarantors, survey (5c-5e) → `app.post_sale_core(..., p_customer_id, ..., p_payments, ..., p_pay_amount => down_payment)` → contract number `app.next_document_number(org, branch, 'contract')` (CT) → `contracts` row → version-1 `schedule_lines` → `app.attach_contract_guarantors` → `app.use_credit_approval` (when an approval was used; also stored in `contracts.credit_approval_id`) → audit `contract.created` → answer. Number taken after every check, so a refused sale takes none (S01 decision 11).
7. **Sale core change (the only change to S01-S03 code):** `app.post_sale_core` gets one new trailing parameter `p_pay_amount numeric DEFAULT NULL` (NULL = the sale total, today's behaviour). N02 passes the down payment. The payment lines must add up to it exactly (`PAYMENT_TOTAL_MISMATCH {total, paid}`, S02). **A down payment of 0.00** (allowed when the policy's minimum is 0) posts **no** payment row: `payments` must then be absent or empty (otherwise `VALIDATION_FAILED`) and the core skips `app.post_sale_payments`. Recreate the core the way S02/S03 did (`DROP FUNCTION` with the full old signature, `CREATE` with the new one); `public.post_sale` keeps calling it unchanged. The S01/S02/S03 SQL tests must still pass untouched.
8. **Down payment methods:** the S02 methods: cash (into the shift's drawer, the slice's "the down payment is in the drawer"), bank transfer (bank account + reference, no shift), store credit (the customer's balance). Allocations go to the **sale** (`payment_allocations.sale_id`), as S02 does; nothing is allocated to schedule lines (that is N03). So `v_sale_balances.unpaid` = total − down payment − financed = **0**, and R02's statement reads: sale (debit, cash price) − down payment (credit) + contract markup (debit) = total payable (tested, decision 14).
9. **The contract row:** `number` (CT…), `customer_id`, `branch_id` (shift's), `sale_id` (this sale; `order_id` NULL), `policy_id` (the engine's), `creditor` (left to P04's trigger: don't send it), `cash_price`, `down_payment`, `financed_amount`, `markup_pct`, `markup_amount`, `total_payable`, `installments_count`, `frequency`, `first_due_date`, `current_version` 1, `status` `active`, `credit_approval_id`, `is_migrated` false, `idempotency_key` = the request's key (a separate table from `sales`, so the same key is fine), `created_by` the employee. Schedule lines: `version` 1, `superseded` false, `seq` / `due_date` / `principal` / `profit` from the engine.
10. **Never edited, statuses:** N02 only creates `active` contracts. `trg_contracts_frozen` already refuses term changes (test it: an UPDATE of `total_payable` or `markup_amount` by a writer is refused). The other statuses belong to later slices: `completed` (N03, last payment), `rescheduled` / `written_off` (N05), `returned` (S05). Add no route that changes a contract. `schedule_lines` stay append-only except `superseded` (baseline).
11. **Dates:** the engine's due dates are already in the shop timezone (`app.org_today`) with month-end clamping (N01). The sale's `business_date` and the contract's `created_at` are the same transaction; N01's trigger recomputes with the shop date of `created_at`, so a sale made at 23:59 Cairo time must still pass (test it with a fixed `now()` near midnight UTC/Cairo if the test setup allows; else note it).
12. **VAT on the markup:** the sale's VAT is on the goods at the cash price (T01, unchanged). `org_settings.installment_markup_vat` = `not_taxed` (default) → no VAT on the profit. `taxed` → refuse the sale with new `MARKUP_VAT_NOT_SUPPORTED` (409) until the accountant answers how it is taxed and invoiced (D41). *To confirm with the accountant.* The ETA e-receipt (T02) stays the sale's, at the cash price.
13. **Contract from an order:** not built. `contracts.order_id` (S10 furniture orders) waits for the Sharia advisor's answer on Islamic finance rule 7. Only `sale_id` contracts here.
14. **R02's rule (D74) holds:** what the customer owes on a contract = its schedule lines; nothing else changes it here. R02's open balance for the customer after an N02 sale = `total_payable`, and the statement's closing balance = `total_due − store credit` (tested on a real N02 sale, not a seeded one).
15. **Audit:** the core still writes `sale.created` (unchanged, its `after` lists the payments = the down payment). Plus one row `contract.created` (severity `info`; `warning` when a credit exception was used), branch set, entity the contract, `after` = number, sale number, customer, cash price, down payment, financed, markup %, markup, total payable, count, frequency, first and last due date, policy version, guarantor ids, credit approval id. Register it in the audit registry with a driver.
16. **Answer** (`InstallmentSale`): `{ sale: Sale (S01's answer, unchanged), contract: Contract }`. A repeat with the same key returns the same answer. A key already used by a **cash** sale → `IDEMPOTENCY_CONFLICT` (the sale exists, no contract).
17. **Read:** `GET /api/contracts/:id` → `public.get_contract(p_id)`: header, customer (name, phone; masking as R01), guarantors (names, relation), the current schedule with each line's status from `v_schedule_line_status`, the balance from `v_contract_balances`, the sale number. Rule 3 (words): every user-visible text, OpenAPI description, receipt and translation says **profit / ربح** and **installment price / سعر البيع بالتقسيط**, never interest / فائدة / loan / قرض. Rule 6: nothing here promises an early-settlement discount. Rule 7: decision 13.

Reuse every code of S01-S03, R03-R05 and N01 above, `INSTALLMENTS_DISABLED`, `SHIFT_REQUIRED`, `SHIFT_CLOSED`, `DAY_CLOSED`, `MODULE_NOT_IN_PLAN`, `PERMISSION_DENIED`, `IDEMPOTENCY_CONFLICT`, `VALIDATION_FAILED`.
