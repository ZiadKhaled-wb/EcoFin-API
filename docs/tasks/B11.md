## Goal
Every audited write records who, where (branch, device, IP), when and with which request id; the owner can search and filter the log on a screen.

## Slice text (F07)
- Written in the same database transaction as the change (if the change fails, no log; if the log fails, no change)
- Stores: user, branch, device, IP, time, action, record, reason (required for sensitive actions), values before and after
- Append-only: no update or delete, even for the owner
- Covers login, logout, failed login, every money and stock action, permission changes, settings changes, exports
- A screen for the owner to search and filter the log
**Done when (slice):** every write endpoint produces an audit entry (checked by a test); the database rejects update/delete on the audit table.

## Database facts (baseline, already there)
`audit_log (organization_id, branch_id, employee_id, super_admin_id, device_id, ip, user_agent, request_id, action, entity_type, entity_id, severity, reason, before, after, created_at)`, append-only by trigger, read policy `audit_log_tenant_read` (needs `audit.view`). `app.write_audit(...)` takes ip from the `x-forwarded-for` request header (first entry), device from `x-device-id` (ignored unless it's a device of the org), `user-agent` and `x-request-id` from `request.headers`. That's the PostgREST request headers the API sends. Failed logins live in `login_attempts` (F04), not `audit_log`.

## Contract
`@ecotech/contracts` audit module: search query (date range, actor, action, entity type/id, branch, pagination) + response rows. Endpoint `GET /api/audit` (use the contract's path if it defines one), permission `audit.view`. If a schema is missing, **stop and report**.

## Behaviour (server)
1. **Audit wiring:** `supabaseForRequest` (F04/F05) forwards on every DB call: `x-request-id` (F08's request id), `x-device-id` (from the client header, only if it's a UUID), `user-agent`, and `x-forwarded-for` set to the **client IP as Express resolved it** behind `trust proxy` (F08), never the raw client-supplied header chain. Unit-test the headers the client is built with.
2. **Search endpoint** `GET /api/audit` with `requirePermission('audit.view')` (F06), `validate` (F05), reading `audit_log` through `req.ctx.db` (RLS scopes the org; never add an org filter from the request). Filters and pagination per contract, newest first, `pageSize` ≤ 100. PII never appears (`write_audit` strips it). Add a cross-shop case (F05 harness).
3. **"Every write endpoint produces an audit entry" check:** a registry, in the style of F05's route check, that lists every non-GET route and the audit `action` it must produce; a unit test fails if a non-GET route isn't in it (public auth routes that write no audit, e.g. forgot-password, are listed with `none` and a reason). Integration tests (`RUN_INTEGRATION=1`) call each write route and assert one new `audit_log` row with the right action, request id and IP.
4. **DB check:** `supabase/tests/f07_audit_test.sql`: as owner (`authenticated` with org claims) and as `postgres`, `UPDATE`/`DELETE` on `audit_log` raise `APPEND_ONLY` (or the baseline's error); `write_audit` stores the request id, IP and user agent from `request.headers`; a forged `x-device-id` of another org is dropped; a cashier without `audit.view` reads zero rows.
5. Only if the search can't be done efficiently or safely with RLS reads, add a read function in migration slot `20261003110000`; otherwise leave the slot unused.
