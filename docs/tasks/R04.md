## Goal
A shop that sells on installments records the people who guarantee a customer's debt. A guarantor is entered once per shop (with the same national ID rules and masking as customers, and ID photos), linked to one or more customers with the relation (father, brother, colleague…), and later attached to specific installment contracts. The installment policy says above which financed amount a contract needs guarantors, and **how many**. The server refuses a contract that needs guarantors and has fewer, even when the client calls the database directly.

## Slice text (R04)
- **Includes:** guarantor details (same ID rules and masking as customers), relation to the customer, ID photos; link guarantors to a customer and to specific contracts; settings define how many guarantors a contract needs above an amount.
- **Done when:** editing a customer never deletes their guarantors; a contract that needs a guarantor can't be created without one.

## Decisions (record them in D71; the ones marked *owner* were confirmed by the owner on 14 Oct 2026: don't change them)
1. **One guarantor record per person per shop.** A guarantor lives in `guarantors` and may back several customers (`customer_guarantors`, with the relation) and several contracts (`contract_guarantors`). Not a shared `persons` table (Data Model §11.1 open point: closed as "separate table + optional `customer_id` link").
2. **Fields:** `full_name` (required, trimmed, 2–150), `phone` (**required**, one number, stored with R01's `app.normalize_customer_phone`), `national_id` (**required**, *owner*: a guarantor only exists to back installment debt, and R01 already requires a national ID for installment customers), `address` (≤ 300), `job` (≤ 100), `monthly_income` (money ≥ 0, optional). No birth date or gender columns: the read answer **derives** `birth_date` and `gender` from the ID with `app.parse_national_id` (only when the caller may see the full ID; otherwise null).
3. **National ID rules = R01 (D63):** 14 digits, Arabic/Persian digits accepted and stored as ASCII (`app.ascii_digits`), must parse (`app.parse_national_id`, birth date not in the future), unique per shop among guarantors (baseline index `guarantors_national_id_idx`) → `GUARANTOR_NATIONAL_ID_TAKEN` with `{ guarantor_id, full_name }` in the details so the screen can offer "link the existing guarantor" instead. Changing the ID of an existing guarantor needs `customer.view_pii` as well (R01 rule 3), whatever the value.
4. **Masking = R01:** `national_id` only for a caller with `customer.view_pii`; everyone else gets `national_id_masked` (`app.mask_national_id`). The audit log never holds the number (mask + `national_id_changed: true` only).
5. **Also a customer:** on create and on an ID change, `guarantors.customer_id` is set to the shop's customer with the same national ID (or NULL). Informational only: the screen shows "also a customer" with a link. A guarantor can't guarantee **themselves**: linking a guarantor whose `customer_id` (or national ID) equals the customer → `GUARANTOR_IS_CUSTOMER`.
6. **Who (no new permission keys; `permissions.ts` must keep equalling the baseline seed):**
   - **Read** (lists, details, a customer's guarantors, the requirement check): the R01 read guard `app.customer_read_guard()` (any rule-6 key, plan module `customers`). Works in an expired (read-only) shop.
   - **Create a guarantor and link it to a customer:** `guarantor.manage` **or** `customer.create` (*owner*: whoever registers the customer at the counter, the cashier included, can register their guarantors; mirrors R01 where `customer.create` creates and `customer.edit` edits).
   - **Edit a guarantor, change a relation, unlink, archive, restore:** `guarantor.manage`.
   - Every write: plan module `customers`; an expired shop can't write (`app.require_permission` already refuses).
7. **ID photos = F14 files**, purpose `customer_id`, **entity type `guarantor`** (new: add `guarantor: 'guarantors'` to `ENTITY_TABLES` in `src/services/files.rules.ts` and `WHEN 'guarantor' THEN 'guarantors'` to `public.register_file`'s entity map; re-create the function from its **latest** version in `20261013010000_s12_warranty.sql`, change nothing else). Upload: the purpose's key (`customer.create`, unchanged); read: `customer.view_pii` (unchanged). The guarantor answer carries `id_photos_count`. `guarantors.id_file_id` does not exist; don't add one.
8. **Relation** (`customer_guarantors.relation`, text in the baseline): one of `father, mother, brother, sister, spouse, son, daughter, relative, friend, colleague, employer, neighbour, other` (*owner* list), required when linking. Checked in the function (no enum, no CHECK change).
9. **Customer links:**
   - Linked and unlinked **one at a time**. No "replace the list" call exists, so **editing a customer (R01 `update_customer`) never touches `customer_guarantors`** — the test proves it.
   - At most **5** guarantors per customer (*owner*) → `GUARANTOR_LIMIT_REACHED`. Linking the same pair twice → `GUARANTOR_ALREADY_LINKED`.
   - An archived guarantor or a blocked/archived customer can't get a **new** link → `GUARANTOR_ARCHIVED` / `CUSTOMER_BLOCKED` (reuse if the code exists, else add it).
   - **Unlink** is refused while the guarantor is on an **active** contract of that customer → `GUARANTOR_ON_ACTIVE_CONTRACT`. Otherwise the `customer_guarantors` row is deleted (the baseline allows deletes on that table); the audit row keeps who, when and the relation.
10. **Archive / restore:** `archived_at = now()` / NULL. Archive refused while the guarantor is on any active contract (`GUARANTOR_ON_ACTIVE_CONTRACT`). An archived guarantor stays readable, keeps its links and contract history, but can't be linked or attached anew. Same state again = no change, no audit row.
11. **Settings: how many guarantors above an amount.** Add one column to the immutable policy versions: `installment_policies.guarantors_required_count smallint NOT NULL DEFAULT 1 CHECK (guarantors_required_count BETWEEN 1 AND 3)`. `publish_installment_policy` accepts the key (add it to `v_keys`), the policy JSON returns it, the contracts' `policyFields` gets it. Existing versions get 1 (no new version is published by the migration). Meaning: when `guarantor_required_above` is not NULL and the contract's **financed amount** (`cash_price − down_payment`, *owner*: the money at risk, not the total with markup) is **greater than** it, the contract needs at least `guarantors_required_count` guarantors. `guarantor_required_above` NULL = never required. A contract may carry at most **3** guarantors.
12. **Contract rules (for N01/N02; no route of their own):**
    - `app.guarantors_required(p_org uuid, p_policy_id uuid, p_financed_amount numeric) RETURNS integer` — 0 when not required, else the count from that policy version.
    - `app.check_contract_guarantors(p_org uuid, p_customer_id uuid, p_policy_id uuid, p_financed_amount numeric, p_guarantor_ids uuid[]) RETURNS void` — raises, in this order: duplicates or more than 3 → `VALIDATION_FAILED: guarantor_ids`; an id not in the shop → `GUARANTOR_NOT_FOUND`; archived → `GUARANTOR_ARCHIVED`; not linked to that customer → `GUARANTOR_NOT_LINKED`; fewer than required → `GUARANTOR_REQUIRED` with `{ required, given }` in the details.
    - `app.attach_contract_guarantors(p_org uuid, p_contract_id uuid, p_guarantor_ids uuid[]) RETURNS void` — inserts the `contract_guarantors` rows (already append-only in the baseline: never removed; N05 changes go through new records).
    - **Safety net:** a `CONSTRAINT TRIGGER trg_contracts_guarantors_check AFTER INSERT ON public.contracts DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` that, at commit, counts the contract's `contract_guarantors` and raises `GUARANTOR_REQUIRED` when below `app.guarantors_required(org, NEW.policy_id, NEW.financed_amount)`. Skipped for `is_migrated` contracts (M02 opening balances; *owner*). This is what makes "a contract that needs a guarantor can't be created without one" true for any writer.
    - Helpers are **not granted** to `authenticated` (SECURITY DEFINER callers only).
13. **Audit actions:** `guarantor.created`, `guarantor.updated` (before/after of the editable fields, ID as mask only; `warning` when the ID changed), `guarantor.archived` (`warning`), `guarantor.restored`, `customer.guarantor_linked`, `customer.guarantor_relation_set`, `customer.guarantor_unlinked` (`warning`). Entity type `guarantor` for the first four, `customer` for the link actions (with `guarantor_id` and `relation` in `after`/`before`).
