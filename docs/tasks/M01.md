## Goal
A shop moving to EcoFin loads what it already has from Excel or CSV: its **products**, **customers**, **suppliers** and **opening stock** per branch. The owner downloads a template, fills it, uploads it, and first gets a **dry run**: every row checked, every error listed by row and column, nothing saved. Only a file with **zero errors** can be imported, and then it is saved **all or nothing**. Opening stock goes into the ledger as **`opening`** movements (with serials for serialized products) so stock equals the file. Importing the same file again **updates** the matching records instead of creating duplicates.

## What exists already (don't rebuild)
- `public.import_jobs` (baseline): `kind` (`products`, `customers`, `suppliers`, `opening_stock`, …), `status` (`uploaded` → `validating` → `validated` → `importing` → `completed` / `failed` / `cancelled`), `file_id`, `result_file_id`, `dry_run`, `rows_total/ok/failed`, `report jsonb`. Frozen once `completed` / `cancelled` (`trg_import_jobs_final`). RLS read needs `import.data` or `export.data`. Unique idempotency key in `report` (I04).
- Permission `import.data` ("Import data and opening balances"): **OWNER only** by default (excluded from BRANCH_MANAGER in the baseline role defaults). No new permission key is needed.
- F14 upload: purpose `import` accepts **csv / xlsx** (detected from the bytes, never the name), needs `import.data`.
- `stock_movement_type 'opening'`, `doc_type 'import'`: I04 `register_units` already posts serials as `opening` movements with `source_type 'import'`, `source_id = import_jobs.id`.
- The sale core takes the cost of a non-serialized product from `products.avg_cost` (S01); a serialized unit carries its own `units.cost`.

## Decisions (recorded in D83)
1. **One kind per file.** `products`, `customers`, `suppliers`, `opening_stock`. The order a shop follows: suppliers → products → customers → opening stock (opening stock needs the products). Columns are defined once in contracts (`IMPORT_COLUMNS`): the template, the header matching and the mapping screen all read that list. A file does not have to use the template's headers: see decision 12.
2. **Node reads the file, SQL decides.** The API downloads the uploaded file (service role, the caller's shop only), detects its type again from the bytes, parses it into plain rows (`{ row: number, values: Record<column, string> }`, every cell as trimmed text; Arabic-Indic digits turned into ASCII; empty rows skipped), and passes them as JSON to SQL. **All rules, matching and writes are in SQL** (`app.import_check_<kind>` and `app.import_apply_<kind>`), so the dry run and the import use exactly the same checks. Node never writes rows itself.
3. **Dry run = no writes except the job row.** `public.create_import(p_kind, p_file_id, p_branch_id, p_rows jsonb, p_idempotency_key)` → `import.data`, the kind's module (`customers` for customers, `serials` when the file has serials), branch access for opening stock. It inserts the `import_jobs` row, runs the check, and stores in `report`: `{ columns, warnings[], errors[{ row, column, code, message }], actions{ create, update, unchanged }, preview[first 20 rows with their action], will_create_categories[] }`, status `validated` (0 errors) or `failed` (≥ 1 error). **Every** error is listed, not just the first. Same idempotency key twice → the same job back.
4. **Import = all or nothing.** `POST /api/imports/:id/run` queues job `import.apply` (only from `validated`, else `IMPORT_NOT_VALIDATED` 409). The worker calls `public.jobs_import_apply(p_job_id)` (service role, acts as the job's `created_by`): one transaction, **re-runs the check first** (data may have changed since the dry run); any error → nothing saved, status `failed`, the new errors in the report. Otherwise applies every row, sets `completed`, counts, `finished_at`, writes the one audit row (decision 9). A retried job on a `completed` job does nothing.
5. **Matching (re-import updates, never duplicates):**
   - **Products:** by `sku` (unique per shop). Archived match → row error `PRODUCT_ARCHIVED` (restore it first). `barcode` taken by another product → `PRODUCT_BARCODE_TAKEN`. Empty barcode on create → generated (C02 rule). `is_serialized` can't change once the product has units or movements (C02 rule). Price changes are allowed (the owner holds every key). `avg_cost` is never a column.
   - **Suppliers:** by name (trimmed, case-insensitive) among **active** suppliers, else by normalised phone. Archived ones don't match (U01 rule 1) and a new supplier is created.
   - **Customers:** owner question 3. National ID must parse (R01 rule 1); birth date and gender come from it. A row that would change an existing customer's national ID → `CUSTOMER_NATIONAL_ID_LOCKED`. Phones: up to 5 in one cell separated by `;`, normalised like R01. `status`, `credit_limit` and ID photos are **not** importable (R01 / R03 own them).
   - **Unchanged** rows (every value equals the record) are counted, not written.
   - The same key twice **inside one file** → row error `IMPORT_DUPLICATE_ROW` on the second one (with the first row's number).
6. **Opening stock** (`opening_stock`, one branch per file, chosen on upload): columns `sku` (or `barcode`), `quantity` (integer > 0) or `serial` (serialized products: **one row per serial**), `unit_cost`. Writes `stock_movements` rows `type 'opening'`, `source_type 'import'`, `source_id = job id`, `stock_state 'sellable'`; serials through `app.create_units` (same rules: `SERIAL_INVALID`, `SERIAL_TAKEN`). Re-import: owner question 5 (difference while only opening movements exist; serials in stock from an opening and missing from the new file are taken out with an `opening` −1; new serials added). Average cost: owner question 6. Rows lock stock in product order (no deadlock with a sale).
7. **Error file.** A failed dry run also writes a CSV (UTF-8 with BOM so Arabic opens in Excel; cells starting with `= + - @` prefixed with `'`) with the original row number, column, code and message, as a `files` row purpose `export`, linked as `result_file_id`; the Web downloads it through the existing files API (signed link). No new route for it.
8. **Templates.** `GET /api/imports/templates/:kind?format=xlsx|csv`: headers (English key + an Arabic label row the importer skips), and in the xlsx a second sheet "Help" explaining each column: required or not, allowed values and one example (no example row in the Template sheet, decision 13). Built from the column list in contracts, so the template and the parser never disagree.
9. **Audit:** owner question 7. Actions `import.validated` (dry run, counts), `import.started` (run), `import.cancelled` and, written by the job, `import.completed` / `import.failed`. No PII (national IDs) in the audit or the report preview (masked like R01).
10. **Cancel:** `uploaded` / `validated` / `failed` jobs can be cancelled (`cancelled` is final). A job can't be imported twice; importing the same file again = a new dry run (which then mostly shows "update" / "unchanged").
11. **Subscription:** an expired (read-only) shop can't import (`require_permission`, like every write).

12. **General for any shop (added 20 Oct).** (a) Every column has aliases in English and Arabic (`Item Code`, `كود الصنف`, `الباركود`, `سعر البيع`...); headers are compared after removing case, spaces, punctuation, diacritics, Arabic letter variants and the Arabic article "ال". (b) `POST /api/imports/inspect` reads the file and answers the sheets, the headers, the first rows and the automatic mapping (which headers match which fields, which are unused, which required fields are missing); nothing is created. (c) `POST /api/imports` takes an optional `mapping` (field → header) that replaces the automatic one; the Web mapping step edits it. (d) A product needs a SKU **or** a barcode (a barcode is used as the SKU when the SKU is empty) and an Arabic **or** English name. (e) CSV: comma, semicolon or tab; UTF-8 (BOM or not), UTF-16 or Windows-1256 (what Arabic Excel saves); Arabic-Indic digits in numbers, dates and phones; dates `YYYY-MM-DD` or day first (`31/12/1990`); phones separated by `; , ، | /` or a new line.
13. **Where the build left the spec (D83 has the reasons):** the template has no example row (the example per column is in the Help sheet; an example row left in the file would import); an empty cell leaves the stored value alone; `quantity` 0 is allowed in opening stock (sets it to zero); a cost-only change of opening stock is ignored; a supplier matched by phone is renamed to the file's name; `import.data` alone is not enough (the importer must also hold the kind's write keys); the worker reads the file again instead of the report storing the rows.

## Template columns (contracts `IMPORT_COLUMNS`)
| Kind | Required | Optional |
|---|---|---|
| products | `sku`, `name_ar`, `cash_price` | `name_en`, `barcode`, `category` (path with `>`), `unit_of_measure`, `installment_price`, `tax_class` (name; empty = shop default), `warranty_months`, `is_serialized` (yes/no, نعم/لا), `min_stock`, `eta_item_code`, `eta_item_type` |
| suppliers | `name` | `phone`, `tax_registration_no`, `address`, `payment_terms_days`, `notes` |
| customers | `full_name`, `phones` | `national_id`, `birth_date` (only without an ID), `gender` (only without an ID), `address`, `city`, `job`, `employer`, `monthly_income`, `is_business`, `tax_registration_no` (required when `is_business`), `notes` |
| opening_stock | `sku` or `barcode`, `unit_cost`, and `quantity` **or** `serial` | — |

Money: digits with up to 2 decimals (`1500`, `1500.50`; thousands separators refused with a clear message). Dates `YYYY-MM-DD` (Excel date cells are converted). Booleans `yes/no/true/false/1/0/نعم/لا`.

## Routes (7)
1. `GET /api/imports/templates/:kind?format=xlsx|csv` → file download (`import.data`).
2. `POST /api/imports/inspect` body `{ kind, file_id, sheet? }` → the sheets, headers, first rows and the suggested mapping (`import.data`; saves nothing).
3. `POST /api/imports` body `{ kind, file_id, branch_id?, sheet?, mapping?, idempotency_key }` (strict) → parse + `public.create_import(...)` → the job with its report (dry run). `branch_id` required for `opening_stock` only.
4. `GET /api/imports?kind=&status=&limit=&cursor=` → `public.list_import_jobs(p_filters jsonb)`: newest first, keyset cursor, `limit` 1-100 (default 25). Reads use `app.has_permission` (an expired shop can still read its history).
5. `GET /api/imports/:id` → `public.get_import_job(p_id)`: the job + full report.
6. `POST /api/imports/:id/run` body `{ idempotency_key }` → queues `import.apply`; answers `202` with the job (`importing`).
7. `POST /api/imports/:id/cancel` → `public.cancel_import_job(p_id)`.
New errors: `IMPORT_MAPPING_INVALID` (422: a header that is not in the file, or one header for two fields), `IMPORT_FILE_UNREADABLE` (422: not csv/xlsx, broken zip, password-protected, empty), `IMPORT_MISSING_COLUMNS` (422, `{columns}`), `IMPORT_TOO_MANY_ROWS` (413), `IMPORT_SHEET_NOT_FOUND` (422), `IMPORT_NOT_VALIDATED` (409, `{status}`), `IMPORT_JOB_NOT_FOUND` (404; another shop's id too). Row-level codes (only inside the report, never an HTTP error): `IMPORT_REQUIRED`, `IMPORT_INVALID_VALUE`, `IMPORT_DUPLICATE_ROW`, `IMPORT_AMBIGUOUS_MATCH`, `PRODUCT_ARCHIVED`, `PRODUCT_NOT_FOUND`, `PRODUCT_BARCODE_TAKEN`, `CUSTOMER_NATIONAL_ID_TAKEN`, `CUSTOMER_NATIONAL_ID_LOCKED`, `NATIONAL_ID_INVALID`, `SUPPLIER_PHONE_TAKEN`, `SERIAL_INVALID`, `SERIAL_TAKEN`, `UNIT_NOT_ALLOWED`, `OPENING_STOCK_LOCKED`, `TAX_CLASS_NOT_FOUND`.

## Done when
- **Errors save nothing:** a products file with errors in 3 rows (missing `name_ar`, bad price, repeated SKU) → dry run lists **all 3** with row and column; the import button is refused (`IMPORT_NOT_VALIDATED`); `products` count unchanged (SQL test + e2e).
- **Clean file imports:** 50 products, 20 suppliers, 30 customers import; every value read back equals the file.
- **Stock equals the file:** opening stock for 10 products (7 bulk, 3 serialized with 5 serials each) in one branch → `stock_levels` = file quantities, 15 `units` in stock, 22 `opening` movements with `source_id` = the job, `avg_cost` = the file cost (one branch) / weighted average (two branches).
- **Re-import updates, never duplicates:** the same products file again → 0 created, 50 unchanged; with 5 prices changed → 5 updated; customers file again → 0 new customers; opening stock with one quantity raised from 10 to 12 → one `+2 opening` movement, stock 12; after a sale of that product → `OPENING_STOCK_LOCKED`.
- **All or nothing at import time:** a product deleted / SKU taken between dry run and import → the job ends `failed`, nothing from the file saved.
- **Safety:** a renamed `.exe` as `.csv` → `IMPORT_FILE_UNREADABLE`; 5,001 rows → `IMPORT_TOO_MANY_ROWS`; another shop's `file_id` → 404; a cashier → 403; national IDs masked in the report preview.
- Local checks green (unit, SQL, integration, Web tsc -b / lint / build / unit / e2e) before any PR; **no merge without the user's OK**.
