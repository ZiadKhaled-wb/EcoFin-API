## Goal
Users log in and out safely with Supabase Auth, every request runs as its own user with a per-request DB client, multi-shop logins pick their shop, and blocked or failing logins are refused and tracked.

## Slice text (F04)
- Login with email or username + password (Supabase Auth)
- Access token + refresh token; the client refreshes silently before expiry
- Real logout that revokes the session on the server
- Forgot-password email and a working reset-password page
- Per-request database access: no shared client that keeps a user session
- Login blocked for inactive users, inactive shops and expired subscriptions (P05)
- Failed-login tracking and rate limiting
**Done when (slice):** two users from two shops log in one after the other and each request still runs as its own user; a token works after refresh; logout makes the old token fail; the reset email leads to a page that changes the password.

## Behaviour
1. **Login** `{ identifier, password, tenantSlug? }`:
   - Email: sign in with Supabase Auth directly. Username: resolve `(tenantSlug, username)` → the employee's login email with the service-role helper (D14), then sign in. Unknown user, wrong password and unknown slug all return the **same** `INVALID_CREDENTIALS` 401 (no user enumeration).
   - Before returning tokens: refuse inactive or archived employees (`ACCOUNT_DISABLED`), inactive shops (`SHOP_INACTIVE`) and expired subscriptions (`SUBSCRIPTION_EXPIRED`), all 403. If the login has several active shops, return them with `requiresShopSelection: true`; the client calls `select-shop` or sends `x-org-id`. If it has exactly one, return it as the active shop. On refusal after a successful password check, revoke the just-created session.
   - Record every attempt in `login_attempts` (service role) with ip and user agent. D17 lockout: ≥ `LOGIN_MAX_FAILURES` failures for the identifier (+ slug) in `LOGIN_WINDOW_MINUTES` → 429 `TOO_MANY_LOGIN_ATTEMPTS` **before** calling Supabase. Keep the per-IP `loginLimiter`.
   - On success: set `last_login_at` and write an audit entry `auth.login` through one `SECURITY DEFINER` function in a **new** migration `supabase/migrations/20261003060000_f04_auth.sql` (rule 11: `SET search_path = ''`, org/employee from the session, `app.write_audit`, `GRANT EXECUTE … TO authenticated`). The same migration adds `public.my_shops()` (SECURITY DEFINER, `STABLE`) returning the caller's active memberships `{org_id, org_name, tenant_slug, role}` for `auth.uid()`, so the API can list shops with the user's JWT (D14). Check whether `app.require_permission` is right for these (login needs no permission key; if `write_audit` needs anything special, follow the baseline). If the baseline already provides something equivalent, use it instead and leave the slot empty.
2. **Per-request client:** `supabaseForRequest(accessToken, orgId?)` creates a fresh client per request with `Authorization: Bearer <user JWT>` and, when present, the `x-org-id` header. No module-level client holds a user session. The `authenticate` middleware validates the token **server-side** with Supabase (`auth.getUser(jwt)`, not just a local JWT decode), so a revoked session fails. Check with Context7 that this is true for the GoTrue version in local Supabase. It puts `{ userId, accessToken, orgId? }` on `req`. `x-org-id` from the client is accepted only if it's a UUID, and the DB still decides whether the caller belongs to it. Loading the employee and enforcing org scope is F05 (B8): don't build that middleware, but leave a clean hook.
3. **Refresh** `{ refreshToken }` → new tokens; an invalid or used refresh token → 401 `TOKEN_INVALID`.
4. **Logout** revokes the session on the server (Supabase sign-out for that session; check the scope options with Context7) and writes an audit entry `auth.logout`. After logout, the old access token fails on `/api/auth/me` (401) and the refresh token fails.
5. **Forgot password** always returns 202 (no enumeration); sends the Supabase recovery email with `redirectTo = FRONTEND_URL + '/reset-password'`. Rate-limited (existing `forgotPasswordLimiter`).
6. **Reset password** `{ recoveryToken | accessToken from the recovery link, newPassword }`: sets the password for that user only, then revokes the user's other sessions. **Change password** (logged in, current + new): verifies the current one, updates, clears `must_change_password` through the DB as the baseline allows (if that needs a write function, put it in the same new migration).
7. The license and activate-workspace flow was already removed in F08 (D15, user decision). Remove the `super_admins` login path only if it's broken against the baseline; otherwise keep it working with `app.is_super_admin()`.
8. Map DB errors with F08's `mapDbError`. Never return raw Supabase or DB messages.
