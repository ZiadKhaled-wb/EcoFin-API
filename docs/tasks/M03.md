## Goal
The owner (or anyone holding `export.data`) presses **Export all data** and, a little later, downloads **one zip** with every table of the shop as **CSV and JSON**: products, units, stock movements, customers, guarantors, sales, contracts, schedules, payments, cash, expenses, suppliers, purchases, tax documents, audit log and the rest, with the ids that link them. Arabic opens correctly in Excel, no cell can run a formula, and the zip carries a manifest with row counts and control totals so the export can be restored into a clean environment and checked (Q04). Every export is audited. It works even when the subscription has expired.

## What exists already (don't rebuild)
- `export.data` ("Export shop data"): OWNER and ACCOUNTANT by role default; **allowed in an expired shop** (P05's `require_permission` exception). No new permission key.
- `import_kind 'full_export'` and `import_jobs` (status `uploaded → … → completed / failed`, `result_file_id`, `report jsonb`): use one `import_jobs` row per export (kind `full_export`) as M01 does for imports; reads of it already need `import.data` or `export.data`.
- F14: files purpose `export` (needs `export.data`), the private bucket written **only** by `storage.service.ts`, `GET /api/files/:id/url` for a short-lived signed download link.
- F13 worker (`src/jobs/registry.ts`): add job type `export.full`.
- `safeCsvCell` (M01): prefixes cells that start with `= + - @` (and tab / carriage return) with `'`; `csv()` writes a UTF-8 BOM and CRLF.

## Decisions (record them in D86)
1. **A background job, one `import_jobs` row per export.** `POST /api/exports` → `public.start_full_export(p_idempotency_key)` (`export.data`): one active export per shop at a time (`EXPORT_RUNNING`, 409, `{ job_id }`); inserts `import_jobs` (kind `full_export`, status `importing`, `dry_run = false`, `report = { requested_by, options }`), queues `export.full` with the job id, audit `export.requested`. Idempotent by key (the same key answers the same job). The worker builds the zip, uploads it, registers the `files` row (purpose `export`) as `result_file_id`, ends the job `completed` with the manifest in `report`; any failure ends it `failed` (`jobs_export_fail`) and logs at error level; audit `export.completed` / `export.failed`.
2. **Which tables (generic, so new tables are never forgotten):** every `public` base table that has `organization_id`, **except** a short deny list kept in one SQL function `app.export_excluded_tables()` with a reason for each (at least: `jobs`, `login_attempts`, `password_resets`, `auth`-linked session rows, `idempotency` / counter tables, `day_checks`, and anything that only holds secrets). Plus `organizations` (the shop's own row) and `branches`. A test (SQL, like `security_guards_test.sql`) fails when a tenant table is neither exported nor in the deny list with a reason.
3. **Which columns:** all, except a deny list of secret columns in `app.export_excluded_columns()`: `token_hash`, `client_secret_vault_id`, `*_secret*`, `password*`, `pairing_code*`, the ETA signing material. A test lists every column whose name matches `token|secret|password|hash|key` and requires it to be either excluded or allowed with a reason (`idempotency_key` and `sha256` are allowed).
4. **National IDs and other PII:** exported **in full** only when the requester also holds `customer.view_pii` (owner question 2); otherwise masked exactly as R01 masks them (`app.mask_national_id`) in `customers`, `guarantors` and the audit log's before/after. The manifest says which (`pii: "full" | "masked"`).
5. **Reading the rows (never everything in memory):** service-role function `public.jobs_export_page(p_job_id, p_table, p_after_id, p_limit)` returns the next page of one table as `jsonb[]` ordered by `id` (keyset paging, 2 000 rows a page; tables without an `id` column are ordered by their primary key), with the excluded columns removed and PII masked by decision 4, and refuses a table that is not in the export list. Each page is streamed into the zip entry; the CSV header comes from the first page's keys in table column order (`app.export_columns(p_table)`).
6. **The zip:** `ecofin-export-{tenant_slug}-{YYYYMMDD-HHmm}.zip` with `csv/{table}.csv` (UTF-8 with BOM, CRLF, every cell through `safeCsvCell`, `null` as an empty cell, money and quantities as the database text, timestamps ISO 8601 UTC, jsonb as compact JSON text), `json/{table}.json` (a JSON array, values exactly as the database gives them), `manifest.json` and `README.txt` (Arabic and English: what each folder is, that ids link the tables, that the formula guard adds `'`). Written to a temp file on disk, then uploaded (no whole-zip buffer in memory for a big shop).
7. **Manifest (the restore check):** `{ format_version: 1, shop: { id, name, tenant_slug }, exported_at, requested_by, pii, schema: { migration: latest migration name, contracts_version }, tables: [{ name, rows, columns }], totals }` where `totals` is computed by the database in the **same snapshot** as the rows (the job reads everything in one `REPEATABLE READ` transaction, decision 8): `cash_balance_total` (sum of `cash_balances`), `stock_on_hand_total` (sum of `stock_levels.on_hand`), `store_credit_total`, `open_contracts_remaining` (sum of `v_contract_balances.remaining` of open contracts), `sales_total`, `payments_in_total`, `payments_out_total`, `audit_rows`. These are the numbers Q04 compares after a restore.
8. **One consistent snapshot:** the worker opens one database transaction `REPEATABLE READ READ ONLY` (through a service-role connection that supports it; if PostgREST can't hold a transaction across pages, the job uses `pg` directly with the service connection string, owner question 3) so totals and rows agree even while the shop keeps selling.
9. **Limits:** at most **500 MB** uncompressed or **2 million rows** per export (`EXPORT_TOO_LARGE`, the job fails with the numbers and a hint to contact support); one export per shop per hour after a completed one (`EXPORT_TOO_SOON`, 429, `{ retry_after }`); zip files are kept **7 days** then removed by a daily job `export.cleanup` (the `files` row stays with `deleted_at` and the audit row). Owner question 4.
10. **Restore check (Q04's tool, not a product feature):** `scripts/export-restore-check.mjs <zip>`: on a **clean local** Supabase (never a hosted one: refuses any URL that is not localhost), loads `csv/` into the same tables with `session_replication_role = replica` (no triggers, no ledger re-posting), in dependency order (read from foreign keys), then recomputes the manifest totals with the same SQL and prints table by table rows and totals: **expected = found** or the differences, exit 1 on any difference. Documented in `docs/05-operations/export-restore.md`.
11. **Downloads:** `GET /api/exports` (list, newest first: status, requested by, when, size, rows, file id while the file exists) and `GET /api/exports/:id`; the download is F14's signed URL (`GET /api/files/:id/url`, `export.data`); every download is audited by F14 as today (or add `export.downloaded` if F14 doesn't audit reads; say so in D86).
12. **Audit:** `export.requested` (who, options), `export.completed` (rows, size, pii mode, file id), `export.failed` (reason code), severity `warning` for `pii = full` exports. The audit log itself is exported (its last rows will not include the `export.completed` row of this export: the snapshot is taken first).

## Routes (4 new)
1. `POST /api/exports` (Idempotency-Key) body `{ pii?: 'masked' | 'full' }` (strict; `full` needs `customer.view_pii`, else `PERMISSION_DENIED`) → `public.start_full_export(p_body, p_key)` (decision 1). Answer `ExportJob` (202).
2. `GET /api/exports` → `public.list_exports()` (decision 11).
3. `GET /api/exports/:id` → `public.get_export(p_id)` (`EXPORT_NOT_FOUND` for another shop's or unknown id).
4. `POST /api/exports/:id/cancel` → `public.cancel_export(p_id)`: a queued or running export stops at the next page and ends `cancelled`; audit `export.cancelled`.
New errors: `EXPORT_RUNNING` (409, `{ job_id }`), `EXPORT_TOO_SOON` (429, `{ retry_after }`), `EXPORT_NOT_FOUND` (404). Reused: `EXPORT_TOO_LARGE`, `PERMISSION_DENIED`.

## Out of scope
- Importing a full export back into a live shop (the restore script is a check on a clean local database only).
- File binaries (logos, scans, photos): only the `files` rows (owner question 5).
- Scheduled automatic exports, exports to e-mail or cloud drives, per-table exports (I05's stock export stays as it is).

## Owner questions (recommended answer first; build with it unless told otherwise)
1. **Zip library:** `yazl` (small, streaming, no native code) *or* `archiver` (bigger, more features) *or* `fflate`. → **`yazl`**, exact version pinned, `npm audit` clean.
2. **National IDs in the export:** full only for a requester who also holds `customer.view_pii`, masked otherwise, *or* always full (it is the shop's own data). → **Full only with `customer.view_pii`.**
3. **Consistent snapshot:** one `REPEATABLE READ` transaction through a direct `pg` connection (a **second new dependency**, `pg`, plus a new env `DATABASE_URL` for the worker; the API has neither today) *or* page through PostgREST without a snapshot and accept that totals may differ by what was sold during the export. → **One snapshot with `pg`** (the restore check needs exact totals); if a direct connection is not allowed on the host, say so before building.
4. **Limits and retention:** 500 MB / 2 million rows, one export an hour, files kept 7 days, *or* other numbers. → **As written.**
5. **File binaries (logos, ID scans, survey photos):** not in the zip (rows only), *or* included as `files/{id}.{ext}`. → **Not included** (size; they stay in storage and the `files` rows list them).
6. **Who may export:** `export.data` (owner and accountant by default), *or* owner only. → **`export.data`**, with `pii = full` audited at warning.
