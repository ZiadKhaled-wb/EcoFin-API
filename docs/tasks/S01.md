## Goal
A cashier with an open shift turns a cart into a completed cash sale in one request. In one database transaction the server prices the cart, checks and takes the stock, marks each IMEI unit sold, writes the sale with its lines and tax snapshot, takes the cash into the shift's drawer, gives the sale its number and writes the audit row. A retried request returns the same sale. Every later sale type (S02 split payments, S03 discounts, N02 installments, S10 orders) calls the same core.

## Slice text (S01)
- **Includes:** one database transaction (lock stock rows, check availability, stock ledger entries, sale document with lines, tax snapshot, payments (S02), drawer ledger entries, document number, audit); prices come from the server, overrides need `price.override` and are audited; serialized lines name the exact serial and the unit is marked sold; idempotency key; cash sale now, installment (N02) and order (S10) reuse this; clear error codes (out of stock, price changed, shift closed) instead of 500.
- **Done when:** the four ledger/reconciliation checks pass; double-submit creates one sale; the last unit can't be sold twice.

## Decisions (record them in D62)
1. **Who and where:** `sale.create`, module `pos` (`app.require_module('pos')`). The sale belongs to **the caller's open shift** (`app.require_open_shift`, else `SHIFT_REQUIRED`): its branch is the sale's branch and its drawer takes the cash. The request carries no branch. `sales.shift_id` and `sales.device_id` come from the shift.
2. **Lines** (1–100): `{ product_id, quantity, unit_id?, unit_price? }`.
   - A product appears on **one** line, except a serialized product, which has one line per unit. A unit appears once. Otherwise `VALIDATION_FAILED`.
   - An unknown or another shop's product → `PRODUCT_NOT_FOUND`; an archived product → new `PRODUCT_ARCHIVED` (409).
   - **Serialized:** `unit_id` is required (`UNIT_REQUIRED`), quantity is 1, the unit is that product's (`UNIT_PRODUCT_MISMATCH`) and is `in_stock` in the shift's branch (`UNIT_NOT_AVAILABLE`). A unit on a non-serialized line → `UNIT_NOT_ALLOWED`. The baseline unit trigger marks it `sold`; don't update `units` by hand.
3. **Prices come from the server:** the list price is `products.cash_price`. A line's `unit_price` is only read when it **differs** from the list price, and then the caller needs `price.override` → new `PRICE_OVERRIDE_DENIED` (403) without it. Every overridden line is listed in the audit row (`product_id`, `list_price`, `unit_price`). `sale_lines.price_override_approval_id` stays NULL (the on-the-spot approval flow is S03's).
4. **Price changed:** the body carries `expected_total` (what the cashier saw, required). When the server's total differs → new `PRICE_CHANGED` (409, details `{ expected_total, total }`), nothing posted. The client quotes again and shows the new prices.
5. **Tax:** one call of `app.compute_document_tax` with the shop's `org_settings.prices_include_vat` and each line's product tax class rate **now** (an archived class still counts). The sale stores the snapshot: `prices_include_vat`, per line `tax_class_id`, `tax_rate`, `tax_amount`, `line_total`; header `subtotal`, `tax_total`, `total`. Discounts are S03: `discount_total` and every `discount_amount` are 0 here.
6. **Total above 0:** a cart that totals 0.00 → `VALIDATION_FAILED`.
7. **Stock:** lock the `stock_levels` rows of the cart's products in the branch **in product id order** (`FOR UPDATE`), check `available` (on hand − reserved) per line → `OUT_OF_STOCK` (409, details `{ product_id, requested, available }`), then one `stock_movements` row per line: `sale_out`, `-quantity`, `unit_id` for serials, source `sale`. The ledger trigger is the last line of defence (it raises `OUT_OF_STOCK` too).
8. **Cost snapshot:** `sale_lines.unit_cost` = the unit's cost for a serial, else `products.avg_cost`; `sales.cost_total` = Σ quantity × unit_cost, rounded to 2. **Warranty:** `warranty_until` = the business date + `products.warranty_months` when that is above 0 (S12 reads it).
9. **Customer:** optional `customer_id` (NULL = walk-in). It must be the shop's customer → new `CUSTOMER_NOT_FOUND` (404). Customers have no screen until R01, so the Web sends none; the parameter is there for S06, S02 (store credit) and N02.
10. **Money (S01: cash only, exact):** the whole total is paid in cash. One `payments` row (`direction in`, `method cash`, the drawer, the shift, number from `next_document_number(org, branch, 'payment')`, idempotency key `system:sale:<sale id>:1`), one `payment_allocations` row (`sale_id`), one `cash_movements` row (type `sale`, `+total`, the drawer, `shift_id`, source `sale` / the sale id, `note` = the sale number so the shift's drawer ledger shows it). S02 replaces this step with payment lines; write it as its own helper (`app.post_sale_payments`).
11. **Number:** `app.next_document_number(org, branch, 'sale')` (SL), taken after every check so a refused sale takes none.
12. **Idempotent:** `app.lock_idempotency_key`; the same key returns the first sale and changes nothing; `system:` keys are refused. Business date: `app.org_today(org)`. A closed day → `DAY_CLOSED` (the ledger).
13. **Audit:** one row, `sale.created`, branch set, `after` = number, total, tax_total, lines count, customer, shift, overrides (severity `warning` when there is an override).
14. **Structure for reuse:** `public.post_sale` is thin (permission, module, shift, idempotency). The work is in `app.post_sale_core(p_org, p_emp, p_shift public.shifts, p_lines jsonb, p_customer_id uuid, p_expected_total numeric, p_idempotency_key text)` returning the sale id. N02 and S10 will call the core with their own payment step; don't put shift or cash-only assumptions inside the stock, tax and document steps.
15. **Quote:** `POST /api/sales/quote` prices a cart without posting: the same validation of lines and prices (no stock lock; it reports `available` per line), the same tax engine, the same totals. `sale.create`, also in an expired shop (a read). Not audited (registry: `{ none: 'Read-only price quote; nothing is written.' }`).
16. **Read:** `GET /api/sales/:id`: the caller's own sales with `sale.create`; any sale of the caller's branches with `report.view` or `cash.view`. Others → new `SALE_NOT_FOUND` (404). Lists, search, void and reprint are S07.
17. **Not here:** payment methods and change (S02), discounts (S03), receipts (S04), ETA receipts (T02: no `fiscal_documents` row is written yet), returns (S05), void (S07).

## Database facts (baseline; don't alter tables, enums or triggers)
- `sales`: `number, branch_id, device_id, shift_id, customer_id, kind sale_kind ('pos'), is_b2b false, prices_include_vat, subtotal, discount_total, tax_total, total, cost_total, discount_reason, issued_at, business_date, idempotency_key`; CHECK `total = subtotal - discount_total + CASE WHEN prices_include_vat THEN 0 ELSE tax_total END`; unique `(organization_id, idempotency_key)`.
- `sale_lines`: `sale_id, line_no, product_id, unit_id, quantity > 0, unit_price, discount_amount, tax_class_id, tax_rate, tax_amount, line_total, unit_cost, warranty_until, price_override_approval_id`; CHECK `unit_id IS NULL OR quantity = 1`.
- `payments` (`direction, method payment_method (cash, bank_transfer, store_credit), amount > 0, customer_id, cash_account_id, shift_id, reference, received_by, business_date, idempotency_key`) and `payment_allocations` (exactly one target; here `sale_id`).
- `stock_movements` (append-only; the trigger keeps `stock_levels`, refuses below zero with `OUT_OF_STOCK`, and moves a unit's status: `sale_out` → `sold`, refusing a unit that is not in stock in that branch with `UNIT_NOT_AVAILABLE`).
- `cash_movements` (append-only; K02's `trg_cash_movements_c_shift` accepts a row with `shift_id` only on that shift's drawer while it is open → `SHIFT_CLOSED`).
- `app.compute_document_tax(jsonb)`: input `{prices_include_vat, document_discount, lines: [{unit_price, quantity, line_discount, tax_rate}]}`, output per line `net, tax, gross` and the totals, as 2-decimal strings. The same calculation as `computeDocumentTax` in the contracts.
- Permissions: `sale.create` (CASHIER, BRANCH_MANAGER, OWNER), `price.override` (BRANCH_MANAGER, OWNER). Document types `sale` and `payment` exist.

## Contract (`packages/contracts/src/sales.ts`, new; contracts 0.30.0)
- `SaleLineInput` (strict): `{ product_id: Uuid, quantity: int 1–100000, unit_id?: Uuid, unit_price?: Money (≥ 0) }`; refine: with `unit_id` the quantity is 1.
- `SaleCreateBody` (strict): `{ lines: SaleLineInput[] (1–100; a product once unless every one of its lines has a unit; a unit once), customer_id?: Uuid, expected_total: Money }` + `Idempotency-Key`.
- `SaleQuoteBody` (strict): `{ lines, customer_id? }`.
- `SaleQuote`: `{ prices_include_vat, lines: [{ product_id, name_ar, name_en, sku, is_serialized, unit_id, serial, quantity, list_price, unit_price, overridden, tax_rate, tax_amount, line_total, available }], subtotal, tax_total, total }` (all money as `Money`).
- `Sale`: `{ id, number, branch_id, shift_id, shift_number, customer_id, customer_name, prices_include_vat, subtotal, discount_total, tax_total, total, business_date, issued_at, created_by_name, lines: SaleLine[], payments: SalePayment[] }`; `SaleLine`: the quote line without `available`, plus `id, line_no, warranty_until`; `SalePayment`: `{ id, number, method, amount, cash_account_id, cash_account_name, reference }`.
- `SaleIdParams`: `{ id: Uuid }`. `PriceChangedDetail`: `{ expected_total, total }`. `OutOfStockDetail`: `{ product_id, requested, available }`.
- New error codes: `SALE_NOT_FOUND` (404), `CUSTOMER_NOT_FOUND` (404), `PRODUCT_ARCHIVED` (409), `PRICE_CHANGED` (409), `PRICE_OVERRIDE_DENIED` (403).
