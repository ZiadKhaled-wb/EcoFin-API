## Goal
Before the shop lends its own money, the server knows how much more credit a customer can get. Each customer has a credit limit, set by a user with `credit.approve`, with a suggested value from the shop settings (monthly income × multiple). Exposure (unpaid principal of the customer's open contracts) is subtracted from the limit to give the available credit. A profile shows the limit, exposure, available credit, a credit score from the shop's weights, and the payment behaviour. One server function decides whether an installment sale of a given financed amount is allowed; above the available credit (or below the minimum score, or for a customer on watch) it is refused unless a `credit.approve` user approved an exception for that customer and amount. N02 calls this function in its transaction, and a commit-time trigger on `contracts` is the safety net.

## Slice text (R03)
- **Includes:** credit limit per customer (set by a user with `credit.approve`, with a default from settings, e.g. a multiple of income); current exposure = unpaid principal of all active contracts (exposure is zero until N02); payment behaviour summary: on-time %, days late, current overdue; used on the server by the installment sale (N02): a sale above the available limit is blocked unless someone with permission approves the exception.
- **Done when:** the server blocks an installment sale over the limit even if the client sends it directly.

## Decisions (record them in D72; the ones marked *to confirm* are defaults: list them in your summary and in a Jira comment for the owner before Part B)
1. **The limit is explicit.** `customers.credit_limit` is the only limit. `suggested_limit = monthly_income × credit_limit_income_multiple` (rounded down to the pound; null when either is null) is shown in the profile and prefills the dialog, but is never used by the check (*to confirm*: the alternative is "0 means use the suggestion"). A new customer's limit stays 0, so no installment sale passes without a limit or an exception.
2. **Setting the limit:** `public.set_customer_credit_limit(p_customer_id uuid, p_limit text, p_reason text)`; `credit.approve`, plan module `customers`; limit ≥ 0, ≤ 99 999 999.99; reason required (3–300) when the limit goes **up**, optional when it goes down; same value again = no change, no audit row. A limit below the current exposure is allowed (the customer just can't take more). Archived customers refused (`CUSTOMER_ARCHIVED` if the code exists, else `CUSTOMER_BLOCKED` with a detail).
3. **History:** no new table. The profile returns the last 10 `customer.credit_limit_set` audit rows for the customer (`at, by_name, from, to, reason`).
4. **Exposure and available credit** come from `v_customer_exposure` (statuses `active` and `rescheduled` count). `available = credit_limit − exposure`, may be negative (shown as 0 available and "over limit by …").
5. **Score (0–100, integer, half-up)** from `credit_score_weights` × components in 0..1:
   - `guarantors`: active linked guarantors (R04, not archived) / 2, capped at 1;
   - `income`: 1 when `monthly_income > 0`, else 0;
   - `identity`: 0.5 for a valid national ID + 0.5 for at least one ID photo (F14 purpose `customer_id`, entity `customer`);
   - `residence`: 0 until R05 (R05 will fill it from the latest approved survey; leave a `TODO(R05)` in `app.customer_credit_score`).
   The profile returns the score, each component and its weight, and `min_score`. Read only; nothing is stored.
6. **Behaviour summary** (from `v_schedule_line_status` over the customer's non-migrated and migrated contracts, superseded lines excluded): `due_lines` (due date ≤ today in the shop timezone), `on_time_pct` (lines fully paid by their due date / due lines, null when none; "paid by" = the allocation's payment date ≤ due date), `max_days_late`, `current_overdue_amount`, `overdue_lines`, `open_contracts`, `completed_contracts`. Write the query once in `app.customer_credit_behaviour(p_org, p_customer_id)`.
7. **The check (for N02; no route of its own):** `app.check_customer_credit(p_org uuid, p_customer_id uuid, p_financed_amount numeric, p_approval_id uuid) RETURNS uuid` raises, in this order:
   - customer not in the shop → `CUSTOMER_NOT_FOUND`; `blocked` or archived → `CUSTOMER_BLOCKED` (never overridable);
   - the reasons that need an exception: financed amount > available → `limit`; score < `credit_min_score` → `score`; status `watch` → `watch` (*to confirm*: watch customers need an exception);
   - no reasons → returns NULL; reasons and no approval → `CREDIT_LIMIT_EXCEEDED` (or `CREDIT_SCORE_TOO_LOW` / `CREDIT_CUSTOMER_WATCH` when `limit` is not among them) with details `{ limit, exposure, available, requested, score, min_score, reasons }`;
   - with an approval: it must be kind `credit_exception`, this shop and customer, `approved`, not used (`entity_id` NULL), not expired, and `amount ≥ p_financed_amount`; otherwise `CREDIT_APPROVAL_INVALID`. Returns the approval id; N02 then calls `app.use_credit_approval(p_approval_id, p_contract_id)` to write the contract id into `entity_id` (once).
   - Not granted to `authenticated`.
8. **Exceptions = approvals on the spot (copy S03):** `public.request_credit_exception(p_customer_id uuid, p_financed_amount text, p_reason text)` (any of `sale.create`, `credit.approve`; reason required; stores `payload {limit, exposure, available, score, reasons}` at request time); `public.decide_credit_exception(p_approval_id uuid, p_approve boolean, p_note text)` (`credit.approve`; not the requester unless the decider is the OWNER, *to confirm*; note required to reject); `public.cancel_credit_exception(p_approval_id uuid)` (the requester, while pending); reads `get_credit_exception(p_id)` and `list_credit_exceptions(p_status text)` (pending first). Valid for **24 hours** after the decision (*to confirm*; S03 uses 15 minutes for a cart, an installment sale takes longer) and for one contract. Re-create `app.approvals_freeze` from its **latest** version (S03) so that an approved `credit_exception` may also get its `entity_id` written once; change nothing else.
9. **Safety net:** `CONSTRAINT TRIGGER trg_contracts_credit_check AFTER INSERT ON public.contracts DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` that, at commit, recomputes exposure **without** `NEW` + `NEW.financed_amount` against the limit, and raises `CREDIT_LIMIT_EXCEEDED` unless an approved `credit_exception` approval has `entity_id = NEW.id` and `amount ≥ NEW.financed_amount`. Skipped for `is_migrated` contracts (M02). Blocked customers raise `CUSTOMER_BLOCKED`. This is what makes the "Done when" true for any writer.
10. **Preview read:** `public.get_customer_credit_check(p_customer_id uuid, p_financed_amount text)` returns `{ allowed, reasons, needs_approval, limit, exposure, available, score, min_score, pending_approval_id, approved_approval_id }` without raising (the POS uses it before N02's confirm).
11. **Who (no new permission keys):** reads (profile, preview, exception reads) = the R01 read guard `app.customer_read_guard()`; writes per decisions 2 and 8; plan module `customers`; an expired shop reads but can't write.
12. **Audit actions:** `customer.credit_limit_set` (`before`/`after` limit, reason; `warning` when it goes up), `credit_exception.requested`, `credit_exception.approved` (`warning`), `credit_exception.rejected`, `credit_exception.cancelled`. Entity type `customer` for the first, `approval` for the others.

- `CreditLimitBody` (strict): `{ credit_limit: Money, reason?: string }`.
- `CreditCheckQuery` (strict): `{ financed_amount: Money (> 0) }`; `CreditCheck` per decision 10; `CreditReason = z.enum(['limit','score','watch'])`.
- `CreditExceptionRequestBody` (strict): `{ financed_amount: Money, reason }`; `CreditExceptionDecideBody` (strict): `{ approve: boolean, note?: string }`; `CreditException` (approval shape like `DiscountApproval`: id, customer, amount, reasons, payload snapshot, status, requested_by/at, decided_by/at, note, expires_at, used: boolean); `CreditExceptionList`; `CreditExceptionListQuery = { status: z.enum(['pending','approved','rejected','cancelled','all']).default('pending') }`.

- New error codes (`errors.ts`): `CREDIT_LIMIT_EXCEEDED` (409), `CREDIT_SCORE_TOO_LOW` (409), `CREDIT_CUSTOMER_WATCH` (409), `CREDIT_APPROVAL_INVALID` (409), `CREDIT_REASON_REQUIRED` (400, or reuse `VALIDATION_FAILED: reason`, your choice, say which). Reuse `CUSTOMER_NOT_FOUND`, `CUSTOMER_BLOCKED`, `APPROVAL_NOT_FOUND` / `APPROVAL_NOT_PENDING` if S03 added them, `PERMISSION_DENIED`.
