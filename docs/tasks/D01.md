## Goal
The owner signs in and sees, on the first screen, how the business is doing **today**: sales and collections, cash in the safes, banks, drawers and collectors' wallets, open shifts, the overdue installments, products below their minimum, ETA receipts that need a person, days not closed, and approvals waiting for them. For **all branches** or **one branch**. Every number is a link to the page that lists what is behind it, opened with the **same filters**, and that page adds up to the **same number** (the slice's Done when). The numbers come from SQL; the browser never adds money up.

## Decisions (record them in D87)
1. **One read, built from the same definitions as the detail pages.** `GET /api/dashboard?branch_id` → `public.get_owner_dashboard(p_branch_id uuid DEFAULT NULL)`. It answers `{ business_date, branch_id (null = all), generated_at, tiles: { … } }`. **Every tile is computed by the same SQL the detail page uses**, so they can't drift: where the detail function has the right filters, call it (or a shared `app.` helper extracted from it in this migration without changing its answer); where it doesn't, write the aggregate once as an `app.dashboard_*` helper with the definition written next to it, and make the test compare it with the detail. Never sum in Node.
2. **Today and the branch filter.** `business_date = app.org_today(org)` (the shop's time zone, as K04). `p_branch_id` NULL = every branch the caller can see (`app.has_branch_access`; OWNER = all active branches); a given branch must belong to the shop (`BRANCH_NOT_FOUND`) and be visible (`BRANCH_DENIED`). Inactive branches are left out of "all".
3. **Who sees what (tile by tile).** The read itself needs only a signed-in employee of the shop (it works in an **expired** shop, like every read). Each tile is present only if the caller holds the key its detail page needs; otherwise the tile is `null` and the Web doesn't draw it:
   | Tile | Needs | Detail page (link with the same filters) |
   |---|---|---|
   | `sales_today` | `report.view` or `sale.create` | `/sales/history?from={today}&to={today}&branch_id=` |
   | `collections_today` | `day.close` or `cash.view` (it is K04's number) | `/accounting/day-close/{branch}/{today}` (one branch) or `/accounting/day-close` (all) |
   | `cash` | `cash.view` | safes and banks: `/accounting/vaults?branch_id=`; drawers: `/accounting/shifts?status=open&branch_id=`; wallets: `/installments/wallets?branch_id=` |
   | `open_shifts` | `shift.operate` or `cash.view` | `/accounting/shifts?status=open&branch_id=` |
   | `overdue` | `overdue.view` | `/installments/overdue?branch_id=` |
   | `low_stock` | `stock.view` | `/inventory/stock?low=1&branch_id=` |
   | `eta` | `fiscal.view` | `/tax/eta-receipts?situation=problem&branch_id=` |
   | `unclosed_days` | `day.close` or `cash.view` | `/accounting/day-close?branch_id=` |
   | `approvals` | per kind: discount (S03's decide key), purchase (U06's approve key), credit (R03's key) | `/sales/approvals`, `/purchasing/approvals`, `/customers/credit-exceptions` |
   Use the exact keys the detail functions check (read them in the migrations; don't guess). The dashboard never shows a number the caller can't open.
4. **Tile definitions (the numbers):**
   - `sales_today`: `{ count, total, paid_by_method { cash, bank_transfer, store_credit }, on_contract }` = the sales dated today in the branches, **excluding voided ones** (S07's status rule: a sale with a `void` return is `voided`). `count` and `total` must equal `search_sales(p_from = today, p_to = today, p_branch_id)` over all its pages with `status <> 'voided'` (`count` = its `total_count` filtered, `total` = the sum of its `total`). `paid_by_method` and `on_contract` use K04's definitions (D84 decision 2) for the same sales.
   - `collections_today`: `{ count, total, in_field }` = K04's `totals.collections` for today (`count`, `total`, `in_field`), summed over the branches. Must equal `get_day_close_preview(branch, today)` per branch (for an already closed today: the stored `day_closes.totals`).
   - `cash`: `{ safes, banks, drawers, wallets, total_in_branches }` (money). `safes` / `banks` = the sum of `balance` of `list_cash_accounts(p_status => 'active', p_branch_id)` by kind (a shop-wide bank counts only when no branch filter is given, as K01 lists it); `drawers` = the sum of `expected_cash` of the open shifts (`list_shifts` status open); `wallets` = the sum of `balance` of `list_collector_wallets` (branch filter as N06); `total_in_branches` = safes + drawers + wallets (K04's `total_closing_cash` idea; banks apart). Each part must equal its detail.
   - `open_shifts`: `{ count, oldest_opened_at, from_earlier_days }` = open shifts of the branches; `count` equals `list_shifts(status => 'open')`'s total; `from_earlier_days` = opened before today (they block K04's close).
   - `overdue`: `{ contracts, amount, customers }` = `list_overdue_contracts({ branch_id })`'s `totals` (the same object, not recomputed). No fee anywhere (Islamic finance rule 4).
   - `low_stock`: `{ products }` = `low_stock_summary`'s `total` (all branches) or its per-branch `low` (one branch).
   - `eta`: `{ needs_action, blocked, send_failed, rejected, due_soon, overdue }` = `fiscal_alert_summary`'s counts, `needs_action` = blocked + send_failed + rejected + due_soon + overdue (the Web's existing `FiscalAlertBadge` adds the same five). `fiscal_alert_summary` has no branch filter: extract its body into `app.fiscal_alert_counts(org, branch_ids uuid[])`, make `fiscal_alert_summary` call it with the caller's branches (its answer must not change: test it), and call it from the dashboard with the filter. `null` when the shop has no `eta` module.
   - `unclosed_days`: `{ days, branches }` = the number of (branch, day) pairs in `day_close_alerts().branches[].unclosed_days` for the filtered branches (last 14 days, today left out, as K04).
   - `approvals`: `{ discount, purchase, credit, total }` pending counts = the number of rows of `list_discount_approvals('pending')`, `list_purchase_approvals('pending', branch)` and `list_credit_exceptions('pending')` the caller can see (each kind `null` without its key; branch filter only where the list has one, say which in D87).
5. **Speed.** The read must answer in **under 300 ms** on the seed shop and under 1 s on a shop with 50 000 sales and 5 000 contracts (measure on the local stack with a generated data set and write the numbers in D87). Use the existing date / branch indexes; add an index only if a measured plan needs it. No caching table; the Web refreshes.
6. **No new write, no audit.** The dashboard reads only; it is not audited (reads aren't, D19).
7. **Web: the first screen.** `/dashboard` becomes a grid of tiles (Arabic RTL and English): branch picker (the caller's branches + "All branches", remembered per user in `localStorage` like other filters), "Today, {date}" in the shop's time zone (use K04's `shopToday` from `src/pages/accounting/dayCloseShared.ts` or move it to `src/lib/format.ts`), last updated time and a refresh button; refreshes every **60 s** while the page is visible. Each tile: a title, the main number (`formatMoney` / `formatNumber`), one or two sub-lines, a colour only for attention (overdue > 0, ETA needs action > 0, unclosed days > 0, open shifts from earlier days > 0, low stock > 0), and the whole tile is a link to its detail with the same filters. A tile the caller can't see is not drawn; an empty grid shows a short "nothing to show for your role" text. The onboarding card (P02) stays on top for an owner who hasn't finished setup; `LowStockCard` and `DayCloseAlertsCard` move **below** the tiles (they list details; the tiles carry the numbers).
8. **Detail pages accept the filters.** Every link in decision 3 must open its page already filtered. Where a page doesn't read a filter from the URL yet, add it (small, like K04 did for the ETA page): at least `/sales/history` (`from`, `to`, `branch_id`), `/accounting/vaults` (`branch_id`), `/accounting/shifts` (`status`, `branch_id`), `/installments/wallets` (`branch_id`), `/installments/overdue` (`branch_id`), `/inventory/stock` (`low`, `branch_id`: check what it reads today). Don't change what those pages show otherwise.

## Owner questions (recommended answer first; build with it unless told otherwise)
1. **Voided sales in "sales today":** left out (the sales history's status rule), *or* counted with the void shown separately. → **Left out.**
2. **Collections today:** gross collected today (reversals shown on the day close, not on the tile), *or* net of today's reversals. → **Gross, as K04's day close.**
3. **Cash tile:** safes + drawers + wallets as "cash in the branches" with banks shown apart, *or* one total with banks. → **Banks apart.**
4. **Refresh:** every 60 s while the page is open, *or* only on the refresh button. → **Every 60 s.**
5. **Who gets the dashboard:** everyone who signs in, each seeing only the tiles their keys allow, *or* owners and managers only. → **Everyone, per-tile keys.**
6. **Default branch on first open:** "All branches" for someone who can see more than one, their default branch otherwise. → **As written.**
