## Goal
A shop that sells to companies issues them a real tax invoice through the ETA e-invoicing system (B2B), not a consumer receipt. At the POS the cashier picks a business customer and turns on **Tax invoice**; the sale is then sent to the ETA as an **Invoice v1.0**, signed with the shop's e-seal certificate, through the same background-job, retry and monitor plumbing T02/T03 built for receipts. A return of such a sale is sent as a **Credit Note** that references the invoice. Nothing is ever submitted twice, a document the ETA refuses shows the ETA's reason in the T03 monitor and can be fixed and resent, and **Sales → Invoices** (a placeholder today) lists the shop's tax invoices and credit notes and prints them on A4.

## ETA facts (from the SDK, read 24 Oct 2026; step 0 turns them into `docs/eta/EINVOICE_SPEC.md`)
These differ from receipts and drive the design. **When the SDK and this file disagree, the SDK wins: update `EINVOICE_SPEC.md`, then the code, and list it in the summary.**
1. **Token:** `POST {identity}/connect/token`, `grant_type=client_credentials`, the client id and secret as HTTP **Basic** auth (no POS headers). 1 hour; cache one per shop until 60 s before expiry. The same ERP-system credentials T02 stores (`eta_settings.client_id` + the Vault secret) **(unverified that one ERP system may submit both receipts and invoices)**.
2. **Submit:** `POST {api}/api/v1.0/documentsubmissions`, body `{ "documents": [ ... ] }`. **202**: `submissionUUID` (26 characters), `acceptedDocuments[] { uuid (26), longId (42), internalId }`, `rejectedDocuments[] { internalId, error { code, message, target, details[] } }` (a submission can be partly accepted). Errors as for receipts: 400 `BadStructure` / `MaximumSizeExceeded`, 403 `IncorrectSubmitter` / `Forbidden` (the "B2B Deny ERP Submission" tag), 422 `DuplicateSubmission` (same payload in 10 minutes, `Retry-After`), 429, 5xx. The page gives no count or size limit **(unverified: read the governance page; until then send at most 20 documents and 1 MB per submission)**.
3. **The UUID is assigned by the ETA** (26 characters, returned on submit). It is **not** a hash we can compute, so "never twice" can't use T02's lookup by UUID: after an unknown outcome or a 422, search instead: `GET {api}/api/v1.0/documents/search?issueDateFrom=&issueDateTo=&internalID=<our number>&direction=Sent` (UTC, range ≤ 30 days, **1 call every 2 s per taxpayer**).
4. **Poll:** `GET {api}/api/v1.0/documentsubmissions/{submissionUuid}?pageNo=&pageSize=` → `overallStatus` (`in progress`, `valid`, `partially valid`, `invalid`), `documentSummary[] { uuid, longId, internalId, typeName, status: submitted | valid | invalid | rejected | cancelled }`, `documentSummaryMetadata { totalPages, totalCount }`. The reasons of an invalid document: `GET {api}/api/v1.0/documents/{uuid}/details` → `validationResults.validationSteps[] { name, status, error }`.
5. **Documents:** Invoice v1.0 (`documentType` `i`, `documentTypeVersion` `1.0`), Credit Note v1.0 (`c`), Debit Note v1.0 (`d`). Credit and debit notes add `references` (string array of the referenced documents' ETA UUIDs, written after `proformaInvoiceNumber`, before `payment`): same issuer, receiver and activity code as the invoice, the same lines with only quantities and amounts changed, the note's total ≤ the referenced total, issued after it. **v0.9 of each type is v1.0 with signature validation off.**
6. **Signature (v1.0):** `signatures: [{ "signatureType": "I", "value": <Base64 CAdES-BES> }]` per document. It signs the SHA-256 of the **serialized document without `signatures`** (the same serializer as receipts, `ERECEIPT_SPEC.md` §8), with an approved Egyptian **e-seal** (or natural-person) RSA certificate that belongs to the issuer's RIN and is valid on the submission date. **(unverified: detached vs attached content and the signed attributes — content-type, message-digest, signing-time, signing-certificate-v2 — settle them from the SDK's signed sample and the signature-creation page; write them into `EINVOICE_SPEC.md`.)**
7. **Fields** (document order matters for the serializer; take it from the v1.0 page): `issuer { address { branchID, country, governate, regionCity, street, buildingNumber, ... }, type "B", id (RIN), name }`, `receiver { address { country, governate, regionCity, street, buildingNumber, ... }, type "B", id (the buyer's RIN, ≠ the issuer's), name }`, `documentType`, `documentTypeVersion`, `dateTimeIssued` (UTC, not in the future), `taxpayerActivityCode`, `internalID`, optional order/proforma references, `invoiceLines[] { description, itemType, itemCode, unitType, quantity, internalCode, salesTotal, total, valueDifference, totalTaxableFees, netTotal, itemsDiscount, unitValue { currencySold, amountEGP }, discount { rate, amount }, taxableItems[] { taxType, amount, subType, rate } }`, `totalDiscountAmount`, `totalSalesAmount`, `netAmount`, `taxTotals[] { taxType, amount }`, `totalAmount`, `extraDiscountAmount`, `totalItemsDiscountAmount`, `signatures`. Amounts up to 5 decimals.
8. **Cancel** (`PUT {api}/api/v1.0/documents/state/{uuid}/state`), receiver **reject**, and their time limits come from the document type's `workflowParameters` (`GET {api}/api/v1.0/documenttypes/{id}`; the SDK's example: "Rejection time limit in hours" = 72). The **submission deadline** for invoices is not on the pages read **(unverified: find it; until then the monitor uses 7 days after issue, alert at 5 days)**.

## Decisions (record them in D93; the ones marked _default_ are proposed defaults the owner must confirm before the build starts: don't change them without the owner's OK)
1. **What becomes an e-invoice** _default_: a **POS cash sale** (`post_sale`, any S02 payment mix) to a **business customer** with the **Tax invoice** switch on. Installment sales (N02), offline sales (S08: the device can't sign), sales from quotations/orders, and exchanges stay consumer receipts or are refused (decision 9). One sale is either a receipt or an invoice, never both (the baseline's one-fiscal-row-per-sale index).
2. **Marking a sale** _default_: `SaleCreateBody.b2b?: boolean` (default false). The server checks, in this order, inside `post_sale` before anything is written: e-invoices are on for the shop (`eta_settings.is_enabled AND einvoice_enabled`, module `eta`) → else `B2B_NOT_ENABLED`; a customer is given and `is_business` → else `B2B_CUSTOMER_REQUIRED`; the buyer data the ETA needs is complete (decision 3) → else `B2B_CUSTOMER_INCOMPLETE` with `{ fields: string[] }` in the details. The sale is **refused**, not blocked later: the cashier fixes the customer (R01 page) and sells again. Permission: `sale.create` (no new key).
3. **Business customer fields** _default_: two new nullable columns `customers.governorate text` (≤ 100) and `customers.building_number text` (≤ 100), editable on every customer (R01's create/update take them, the customer JSON returns them). For a B2B sale the receiver needs: `tax_registration_no` that is **exactly 9 digits after removing dashes and spaces** and is not the shop's own RIN, `full_name`, `address` (street, ≤ 200), `city`, `governorate`, `building_number`. The RIN keeps R01's stored text (9–20 digits or dashes); the ETA gets the 9 digits. The slice's "type" is fixed `B` (a business in Egypt); foreign buyers (`F`) are out of scope. A pure `b2bReceiverProblems(customer)` in the contracts returns the missing/invalid field names (the server's SQL check and the POS warning use the same rules; a contracts unit test and the SQL test share the cases).
4. **Document type and version** _default_: Invoice and Credit Note **v1.0, signed**. New setting `eta_settings.einvoice_version text NOT NULL DEFAULT '1.0' CHECK (einvoice_version IN ('1.0','0.9'))` with `CHECK (einvoice_version = '1.0' OR environment = 'preprod')`: **0.9 (unsigned) is allowed only on pre-production**, so the format can be proven before the shop has its certificate. Changing the environment to `prod` while `0.9` is set → `VALIDATION_FAILED: einvoice_version`.
5. **Signing** _default_ (the main owner question): the shop's e-seal certificate is uploaded once by the owner as a **PKCS#12 file (.pfx/.p12) with its password**; the API opens it (`pkijs` + `asn1js`, **new dependencies: the owner must approve them**), checks the password, that it holds one RSA key and certificate, that the certificate is valid now, and reads its subject, serial and expiry; the file (Base64) and the password go to **Supabase Vault** like the client secret (`app.eta_put_secret`); the table keeps only vault ids + `signing_cert_subject`, `signing_cert_serial`, `signing_cert_not_after`. Signing runs in the API worker behind a `DocumentSigner` interface (`src/eta/signer.ts`, next to `ReceiptSigner`): `pfxSigner` (CAdES-BES over the SHA-256 of the serialized document, decision 6 of the facts) and `noSignature` for v0.9. Secrets are never logged, returned, audited or put in an error. **If the shop's certificate provider only issues it on a USB token (not exportable), a signing agent on the shop's PC is needed: that is a follow-up slice, not T04.**
6. **Settings** _default_: `eta_settings.einvoice_enabled boolean NOT NULL DEFAULT false`. Turning it on needs T02's settings complete (client id, secret, activity code, `is_enabled`), the shop's RIN (9 digits) and legal/trade name, and, for v1.0, a certificate whose `signing_cert_not_after > now()` → else `EINVOICE_CERTIFICATE_REQUIRED`. Who: `org.settings_manage` (like T02). The new columns follow the `client_secret_vault_id` rule: **no column grant** for the two vault ids; the other new columns are granted for SELECT.
7. **Numbers and dates:** `internalID` = `sales.number` (invoice) / `sales_returns.number` (credit note); `dateTimeIssued` = `sales.issued_at` / the return's `created_at`, cut to whole seconds, UTC (`2026-10-12T09:15:02Z`). Issuer = the sale's branch (`branches.eta_branch_code` → `branchID`, address as T02), `organizations.tax_registration_no`, `legal_name` else `name`, `eta_settings.activity_code`.
8. **Amounts:** exactly T02's mapping from the stored sale lines (`ERECEIPT_SPEC.md` §11), renamed: `salesTotal` = T02's `totalSale`; `discount.amount` = the discount excluding VAT (no `rate`); `netTotal` = `netSale`; `unitValue { currencySold: "EGP", amountEGP: unitPrice (5 decimals) }`; `itemsDiscount`, `valueDifference`, `totalTaxableFees` = `0`; one `T1` taxable item from the line's tax class; `total` = `line_total`. Header: `totalSalesAmount` = Σ `salesTotal`, `totalDiscountAmount` = Σ `discount.amount`, `netAmount` = Σ `netTotal`, `taxTotals` = one `T1` sum, `extraDiscountAmount` = `0`, `totalItemsDiscountAmount` = `0`, `totalAmount` = `sales.total`. `unitType` `EA`, `itemType`/`itemCode` from the product as T02, `internalCode` = SKU, `description` = `name_ar`. Number text rules as T02 (own JSON writer, the exact text stored and sent; `ERECEIPT_SPEC.md` §8 "What rule 3 means").
9. **Credit notes (returns)** _default_: a S05 return of a B2B sale writes a `b2b_credit_note` fiscal row (not `b2c_return`). Lines: the returned sale lines with the returned quantity and S05's cumulative refund, tax and discount for them; `references` = `[the invoice's eta_uuid]`. A credit note is **built only after its invoice is `accepted`** (it waits, like T02 returns wait for the sale's UUID); while the invoice is rejected or blocked, the credit note waits too (the monitor says why). No 540-day rule for credit notes (that is a receipt rule). **Exchanges of a B2B sale are refused** → `EXCHANGE_NOT_FOR_B2B` (do a return, then a new B2B sale).
10. **Debit notes** _default_: **not produced** in T04: no flow raises the amount of an issued sale (documents are immutable, prices fixed at sale). The builder supports type `d` (with a unit test) so a later slice can use it.
11. **Void (S07)** of a B2B sale: the same rule as receipts (allowed only before the document went to the ETA; the fiscal row becomes `cancelled`); once submitted, a return (credit note) is the way. The ETA cancel API, receiver rejections and their notifications are out of scope.
12. **Pipeline (F13 jobs, per shop, not per POS):**
    - The sale (or return) writes the fiscal row (`status 'pending'`, `device_id NULL`, `environment` from the settings, `internal_id` = our number) and queues `eta.invoice.prepare` (dedupe key `eta.invoice.prepare:<org>`) in its own transaction.
    - `eta.invoice.prepare`: loads up to 50 pending B2B rows without a payload (credit notes only when their invoice is accepted), builds the document, checks it (decision 14), serializes it without `signatures`, signs it (v1.0) and stores the exact document JSON text in `payload.document_json` + the SHA-256 of the serialization in `payload.document_hash`; queues `eta.invoice.submit` (`eta.invoice.submit:<org>`).
    - `eta.invoice.submit`: claims prepared rows with a lease (oldest first, ≤ 20 documents and ≤ 1 MB), sends them, maps `acceptedDocuments` → `submitted` (+ `eta_uuid`, `eta_long_id`, `eta_submission_uuid`) and `rejectedDocuments` → `rejected` (the ETA error text in `last_error`), queues `eta.invoice.poll` (`eta.invoice.poll:<submission>:<n>`). After an **unknown** outcome or a **422**: before any resend, search each document by `internalID` and an issue-date window (fact 3, respecting 1 call / 2 s); found → `submitted` with that UUID; not found → `pending`, retried with T02's backoff.
    - `eta.invoice.poll`: `valid` → `accepted`; `invalid` → `rejected` with the reasons from `/details` (masked as T02 masks ETA text); `cancelled` → `cancelled`; still `submitted` → poll again (T02's poll schedule and `poll_timeout` alert).
    - Worker functions (service role only, `public`, like T02's): `eta_invoice_load_pending(p_org uuid, p_limit integer)`, `eta_invoice_credentials(p_org uuid)` (client id, secret, certificate, password, version, environment), `eta_invoice_store_prepared(p_fiscal_id uuid, p_payload jsonb)`, `eta_invoice_block(p_fiscal_id uuid, p_code text, p_message text)`, `eta_invoice_claim_for_submit(p_org uuid, p_limit integer)`, `eta_invoice_mark(p_fiscal_id uuid, p_status public.fiscal_status, p_fields jsonb)` (the transitions of T02's `eta_mark`, but the UUID comes **with** `submitted` and the follow-up jobs are the `eta.invoice.*` ones), `eta_invoice_load_submitted(p_org uuid, p_submission_uuid text)`. T02's `eta_*` device functions are **not** used for B2B rows and must never return them (decision 13).
13. **Keeping receipts and invoices apart:** every T02/T03/S05/S08 loader or worker function that selects `fiscal_submissions` by device or branch must only ever see `b2c_*` rows. Check each (`eta_load_pending_for_device`, `eta_claim_for_submit`, `eta_load_submitted`, `eta_claim_deadline_alerts`, `eta_load_for_correction`, `fiscal_assign_device`, the S08 release functions); where one lacks a `doc_type` filter, re-create it from its **latest** version adding only `AND f.doc_type IN ('b2c_receipt','b2c_return')`. The SQL test proves each one ignores a B2B row.
14. **Blocked documents** (`status 'failed'`, `last_error` starting `BLOCKED:`, fixed by the user then retried with T03's retry): `BLOCKED:SELLER_DATA` (RIN, name, activity code, branch code or branch address missing), `BLOCKED:ITEM_CODE`, `BLOCKED:BUYER_DATA` (the customer was changed after the sale and no longer passes decision 3: the document is built from the **current** customer, the sale itself never changes), `BLOCKED:NO_CERTIFICATE` (v1.0 and no certificate), `BLOCKED:CERTIFICATE_EXPIRED`. A send failure (not blocked) keeps a `SEND:` prefix in `last_error`.
15. **Monitor (T03) shows invoices too:** `app.fiscal_situation` is re-created so a `failed` row is `blocked` when `last_error LIKE 'BLOCKED:%'` (or it has no UUID and no error, the receipt case), else `send_failed` — receipts keep their current situations (T03's SQL test must still pass unchanged). `app.fiscal_deadline_at` gets the B2B deadline (fact 8: 7 days after issue, warning from 5 days) by `doc_type`. **Fix and resend** a rejected invoice or credit note: `fiscal_request_correction` accepts B2B rows and queues `eta.invoice.prepare` after clearing the payload; the rebuilt document is a **new submission** (the ETA gives it a new UUID); the rejected UUID moves to `reference_old_uuid` and stays in `fiscal_events`. T03's "nothing changed" rule applies (compare the rebuilt and stored documents ignoring `signatures`): `CORRECTION_NOTHING_CHANGED`. A credit note whose invoice was resent references the **new** accepted UUID.
16. **List and print:** `fiscal_list` is re-created with one more last parameter `p_kind text DEFAULT NULL` (`receipts` = `b2c_*`, `invoices` = `b2b_*`, NULL = all; anything else `VALIDATION_FAILED`) and each item gains `doc_type` (if missing) and `buyer_name` (the customer's `full_name`, NULL for walk-ins). The A4 tax invoice is drawn and printed by the client (D68's way: no PDF on the server), from the sale answer + `fiscal_details`, with the ETA UUID and a QR of the public link `{portal}/documents/{uuid}/share/{longId}` **(unverified: confirm the share link format in step 0)**; before acceptance the paper says "not yet accepted by the ETA" and has no QR.
17. **Audit:** `eta.einvoice_settings_updated` (before/after of `einvoice_enabled`, `einvoice_version`; `warning` when enabling or changing the version), `eta.certificate_set` (`warning`; subject, serial, expiry only, never the file or the password). The sale's existing `sale.created` audit row gains `b2b: true|false`; nothing else new.
18. **Who (no new permission keys; `permissions.ts` must keep equalling the baseline seed):** settings and certificate `org.settings_manage`; the B2B sale `sale.create` (+ the `sales`/`pos` module checks it already has); list, details, print `fiscal.view`; retry and correction `fiscal.retry`; the `eta` plan module on every write that touches e-invoices.

- ETA document cancellation, receiver rejections and their decline flows, ETA notifications (`receive document notifications`), document packages and printouts from the ETA, late submission requests, received (purchase) invoices from suppliers.
- Changing T02's receipt format, chain or jobs; new permission keys, roles or plan modules.
