## Goal
A cashier (or anyone with `collection.create`) finds a customer or a contract, sees what is due and overdue, and takes a payment on **one contract** in **one request**. In one database transaction the server locks the contract, allocates the amount in a fixed order (fees → oldest installment, profit then principal → next), writes one numbered payment (the receipt) with its allocations, puts cash into the open shift's drawer, turns any overpayment into the customer's store credit, closes the contract when nothing is left, and writes the audit row. No sale, no revenue, no VAT. A retried request returns the same payment.

## Slice text (N03)
- **Includes:** find a customer or contract; see what's due and overdue; take a payment (full, partial or several installments); allocated in a fixed order: late fees → oldest installment (profit, then principal) → next; overpayment becomes customer credit, never lost; payment receipt (numbered, printed); cash goes to the current shift's drawer (or collector wallet, N06); contract balance and status update; fully paid → completed; a collection is **not** a new sale (no new revenue or VAT on the goods); idempotent.
- **Done when:** allocation is the same every time for the same inputs; a double-click records one payment; the last payment closes the contract.

## Decisions (record them in D78; the ones marked *to confirm* are defaults: post them on EC-82 before Part B)
1. **Who and where:** `collection.create` (`app.require_permission`, so an expired, read-only shop is refused), module `installments`. A counter collection belongs to the caller's open shift (`app.require_open_shift`, locked `FOR UPDATE` like `post_sale`), its still-paired device (`app.require_shift_device(shift_id)`, EC-147), `app.require_branch_access(shift branch)`. The payment's branch is the **shift's** branch; the contract may belong to **any branch of the shop** (a customer may pay at any branch) (*to confirm*). The shop's `installments_enabled` switch is **not** checked: switching installments off stops new contracts, never the collection of old ones.
2. **One contract per collection.** `public.post_collection(p_contract_id uuid, p_body jsonb, p_idempotency_key text) RETURNS jsonb`. Body (strict): `{ amount: Money (> 0), method: 'cash' | 'bank_transfer' | 'store_credit', tendered?: Money (cash only, ≥ amount), cash_account_id?: Uuid (bank_transfer only, required), reference?: string 1-100 (bank_transfer only, required), expected_due?: Money }`. **One method per collection** (one payment row = one receipt number) (*to confirm*; split payments as in S02 can come later). Paying several contracts of one customer = several collections; a customer-wide allocation is out of scope (*to confirm*).
3. **Allocation order (fixed, deterministic, in SQL only):** inside `app.collection_allocation(p_org, p_contract_id, p_amount)` (pure read, `STABLE`, no grants; used by the preview and by the write, so both always agree):
   1. **Fees first:** the contract's charges with `due = amount − waived − paid > 0`, ordered by the line's `seq`, then `assessed_on`, then `id`. Each gets `min(left, due)`. (*To confirm* with the Sharia advisor: under `ISLAMIC_FINANCE_RULES.md` rule 4 a charge is a charity penalty, and the slice puts it first; the alternative is installments first, penalties last.)
   2. **Then the current schedule** (`superseded = false`, `version = contracts.current_version`), lines ordered by `seq` (= oldest due date first) with `remaining > 0`. Inside a line: **profit first** (`profit − paid_profit`), **then principal** (`principal − paid_principal`). Moving to the next line only when this one is fully paid.
   3. **What is left** after every fee and line is paid = the **overpayment** → store credit (decision 6).
   Numbers come from `v_schedule_line_status` / the charges' sums over `v_effective_allocations` (a reversed payment never counts). Same contract state + same amount → the same rows in the same order, always (the slice's first Done when, tested by running the function twice and comparing). Splitting profit and principal is accounting only (rule 9): it never changes what the customer owes.
4. **Order inside `post_collection`** (one transaction): body shape → permission, module → idempotency (the same key returns the first answer, changes nothing; a key already used by another payment, e.g. a sale's → `IDEMPOTENCY_CONFLICT`) → shift lock + device + branch access → **contract lock** (`SELECT … FROM contracts WHERE id = $1 AND organization_id = org FOR UPDATE`; not the shop's → `CONTRACT_NOT_FOUND`) → status `active` or `rescheduled`, else new `CONTRACT_NOT_OPEN` (409, `{status}`) → nothing left to pay (remaining + fees = 0) → `CONTRACT_NOT_OPEN` too → `expected_due` given and ≠ the server's current total due → new `COLLECTION_DUE_CHANGED` (409, `{total_due}`: another till took a payment since the screen loaded) → method checks (bank account: the shop's, `kind = 'bank'`, active, `FOR SHARE`; store credit: lock `store_credit_balances` `FOR UPDATE`, `INSUFFICIENT_STORE_CREDIT {balance}` as S02) → allocation (decision 3) → payment number `app.next_document_number(org, shift branch, 'payment')` → `payments` row → allocations → cash movement → store credit movements → completion (decision 7) → audit → answer. Number taken after every check, so a refused collection takes none.
5. **The payment row:** `direction 'in'`, `method`, `amount` = the full amount received (overpayment included), `customer_id` = the contract's customer, `cash_account_id` = the shift's drawer (cash) / the bank account (bank transfer) / NULL (store credit), `shift_id` (cash and bank transfer: the shift; store credit: the shift too, for the till report), `reference`, `tendered` (cash), `received_by` / `created_by` = the employee, `business_date` = `app.org_today(org)`, `idempotency_key` = the request's key. **Allocations:** one row per charge (`charge_id`, `contract_id`, `amount`) and one per schedule line touched (`schedule_line_id`, `contract_id`, `principal_amount`, `profit_amount`, `amount` = their sum). The overpayment is **not** an allocation (decision 6).
6. **Overpayment never lost:** when `amount` > what is due on the contract, the excess goes to one `store_credit_movements` row `+excess` (`source_type 'payment'`, `source_id` = the payment, the shift's branch, the business date). The answer shows `overpayment`; the screen warns before confirming (Part B). **A store-credit collection can't overpay** (moving credit to credit is pointless): `method = store_credit` and `amount` > total due → `VALIDATION_FAILED`. A store-credit collection writes one `store_credit_movements` row `−amount` (`source_type 'payment'`) and no cash movement. R02's statement already treats store-credit payments as non-rows and overpayment credit as a credit (D74): check it on a real N03 payment.
7. **Completion:** after the allocations, if the contract's current-version `remaining` = 0 **and** `fees_due` = 0 → `UPDATE contracts SET status = 'completed', closed_at = now(), updated_by = emp` (the baseline `trg_contracts_frozen` lets status / closed_at move; touch nothing else). Then R03's exposure drops to 0 for it and `v_schedule_line_status` shows `paid`. A completed contract takes no more collections (`CONTRACT_NOT_OPEN`). A `rescheduled` contract completes the same way (its current version paid).
8. **Money in:** cash → one `cash_movements` row on the shift's drawer, `+amount` (the whole amount received, overpayment included: the money is in the drawer), `type 'collection'`, `source_type 'payment'`, `source_id` = the payment, note = payment number + contract number. Bank transfer → one row on the bank account, no shift, as S02 does. The day-close trigger (`DAY_CLOSED`) applies as for sales. Collector wallet (N06) is **not built**: write the core as `app.post_collection_core(p_contract, p_emp, p_branch, p_shift, p_account, p_body, p_key)` so N06 can call it with a wallet account and no shift.
9. **Not a sale:** no `sales` row, no tax, no ETA receipt (T02), no stock, no revenue. The profit part of each allocation is what reports (D0x) later read as installment profit received.
10. **Preview (what is due + what this amount would do):** `GET /api/contracts/:id/collection?amount=` → `public.preview_collection(p_contract_id uuid, p_amount numeric DEFAULT NULL)`: `collection.create` checked with `app.has_permission` (an expired shop may look), module `installments`, the shop's contract (`CONTRACT_NOT_FOUND`). Returns `{ contract: { id, number, status, customer: { id, name, phone }, branch_id, total_payable }, due: { overdue_amount, overdue_lines, due_today, next_due_date, next_due_amount, fees_due, remaining, total_due }, lines: [current version: seq, due_date, amount, paid, remaining, status, days_late], charges: [{ id, seq, assessed_on, amount, due }], allocation?: { lines: [{ seq, profit, principal, amount, pays_off }], charges: [{ id, amount }], overpayment, completes_contract } }` (`allocation` only when `amount` is given; `amount` ≤ 0 or more than 2 decimals → `VALIDATION_FAILED`). `total_due` = `remaining + fees_due` (what closes the contract) and is what the write compares with `expected_due`. Reuse R02's / N02's JSON helpers where the shape matches (say which).
11. **Find a customer or contract:** `GET /api/contracts?q=&customer_id=&status=&branch_id=&overdue=&limit=&cursor=` → `public.list_contracts(p_filters jsonb)`: R01's customer read guard (`app.customer_read_guard`, an expired shop may read) and only the caller's branches (`app.user_branch_ids` or the pattern `get_contract` uses). `q` matches the contract number (prefix, case-insensitive), the customer's name (contains), phone (contains) and national ID (**exact** match only, never shown in the answer). Rows: `{ id, number, status, customer: { id, name, phone }, branch_id, total_payable, paid, remaining, overdue_amount, max_days_late, next_due_date }` from `v_contract_balances`, newest first, keyset cursor (`created_at, id`), `limit` 1-100 (default 25). `overdue=true` → `overdue_amount > 0`. Default status filter: `active` + `rescheduled`.
12. **Receipt and reprint:** `GET /api/collections/:id` → `public.get_collection(p_id uuid)`: the payment (number, method, amount, tendered, change = tendered − amount, reference, business date, paid at, received by name, branch), the contract (number, customer name / phone, status after), the allocations (each line's seq, due date, profit, principal, amount; each fee), the overpayment, and the contract's balance **after this payment** (`remaining`, `next_due_date`, `next_due_amount`) (computed from allocations made up to this payment's `created_at`, *or* stored in the audit `after`; say which you chose). Same read rule as decision 11 plus the payment's branch; not a collection or another shop's → new `COLLECTION_NOT_FOUND` (404). `POST /api/collections/:id/prints` → `public.record_collection_receipt_print(p_id uuid)`: the same rule as S04's `record_sale_receipt_print` (copy it: first print = original, later prints = copy with a count, audit `collection.receipt_printed`). The receipt is not a fiscal document.
13. **Idempotency (the slice's "a double-click records one payment"):** the key lives on `payments.idempotency_key` (unique per shop). The function takes `pg_advisory_xact_lock` on the key (S01's pattern) before reading it, so 20 concurrent requests with one key → one payment, one number, one cash movement, and 19 answers equal to the first. A repeat after the contract was completed still returns the first answer (the idempotency check comes before the status check).
14. **Concurrency:** two tills collecting on one contract serialise on the contract row lock; the second sees the first one's allocations. With `expected_due` the second gets `COLLECTION_DUE_CHANGED`; without it, it is allocated against what is left (and may overpay into store credit). Tested in the proof (Part A step 4).
15. **Audit:** one row `collection.created` (severity `info`; `warning` when there is an overpayment), branch = the shift's branch, entity = the payment, `after` = payment number, contract number, customer, method, amount, allocations (seq / profit / principal, fees), overpayment, contract status after, remaining after. `contract.completed` (severity `info`, entity = the contract) as an extra action when decision 7 closes it (the audit registry's `also`, as N02 did). Register both with a driver.
16. **Islamic finance rules in N03:** rule 3 (words): every user-visible text, OpenAPI description, receipt and translation says **installment / قسط**, **profit / ربح**, **installment price / سعر البيع بالتقسيط**, **collection / تحصيل**, never interest / فائدة / loan / قرض. Rule 4: N03 adds nothing to the debt; a fee is only collected if N04 assessed it. Rule 6: no early-payment discount here (a customer who pays everything pays the remaining installment price; a waiver is N05's).
17. **Reversing a collection** (a wrong amount) is **not** built here: `payments.reverses_payment_id` and `v_effective_allocations` already support it; it comes with N05 or a follow-up (*to confirm*). Note it in the summary.
18. **Errors:** new `CONTRACT_NOT_OPEN` (409, `{status}`), `COLLECTION_DUE_CHANGED` (409, `{total_due}`), `COLLECTION_NOT_FOUND` (404). Reuse `CONTRACT_NOT_FOUND`, `INSUFFICIENT_STORE_CREDIT`, `SHIFT_REQUIRED`, `SHIFT_CLOSED`, `DEVICE_REVOKED`, `DEVICE_MISMATCH`, `DAY_CLOSED`, `MODULE_NOT_IN_PLAN`, `PERMISSION_DENIED`, `IDEMPOTENCY_CONFLICT`, `VALIDATION_FAILED`, `BRANCH_ACCESS_DENIED` (whatever `require_branch_access` raises). Register the details schemas that are not registered yet.
19. **No table, column, enum or permission change.** New functions only. If you find you need a schema change, stop and say why.
