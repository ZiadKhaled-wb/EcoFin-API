## Goal
The owner (or the accountant) sees **who owes the shop money and how late they are**: the open installment balances today, grouped by customer, branch or collector, each split into age buckets (not due, 1-30, 31-60, 61-90, 90+ days late) and into principal and profit; a click on a row drills down to its contracts, and a contract opens its page. **The grand total equals the sum of the open contract balances** to the piaster (the slice's Done when), and the late buckets equal what the overdue list and the D01 tile show. The numbers come from SQL; the browser never adds money up. There are no fees in any column (rule 4).

## Decisions (record them in D91)
1. **One read.** `GET /api/reports/receivables?group_by&branch_id&collector_id&customer_id&q&min_days&sort&page&page_size` → `public.report_receivables(p_group_by text, p_branch_id uuid DEFAULT NULL, p_collector_id text DEFAULT NULL, p_customer_id uuid DEFAULT NULL, p_q text DEFAULT NULL, p_min_days integer DEFAULT NULL, p_sort text DEFAULT 'outstanding_desc', p_page integer DEFAULT 1, p_page_size integer DEFAULT 50)`. It answers `{ as_of, generated_at, group_by, filters, rows: [...], totals: {...}, check: {...}, total_count, page, page_size }`. Every number is a SQL aggregate (`numeric`, sent as a 2-decimal string through `app.report_money`); Node only parses and forwards.
2. **As of today.** The report is the state **now**, in the shop's time zone: `as_of` = the shop's today, the same clock `v_schedule_line_status` uses. No past date (owner question 2): payments and versions as they stood on an earlier day are not rebuilt here.
3. **Which balances count (the definition, used for rows, totals and the check).** Every **current** schedule line (`NOT superseded`) of every **open** contract (`status IN ('active', 'rescheduled')`) of the shop, in the branches the caller can see (decision 6), with something left on it (`remaining > 0`). Closed contracts (`completed`, `written_off`, `returned`) are out, as on the overdue list and R02 (owner question 5 for write-offs). M02 opening contracts count like any other (they store only what is left: D85); `migrated_contracts` in the row says how many. An exchange or a return already lowered the current version (D88): nothing else to subtract.
4. **The measures** (per row and in `totals`; money 2 decimals as strings):
   - `outstanding` = Σ `remaining`; `principal` = Σ `principal_remaining`; `profit` = Σ (`profit` − `paid_profit`). `principal` + `profit` = `outstanding` on every row (allocations split each payment into profit and principal: N03); test it.
   - **Buckets** of `outstanding`, by the line's status and `days_late` from `v_schedule_line_status` (the N04 definition, owner question 1): `not_due` = lines whose status is `upcoming`, `due` or `partly_paid` (not yet due, due today, or inside the grace days); `late_1_30`, `late_31_60`, `late_61_90`, `late_90_plus` = lines whose status is `overdue`, by `days_late` (counted from the due date) 1-30, 31-60, 61-90, above 90. Σ buckets = `outstanding` on every row. These are exactly `v_receivables_aging`'s columns and `list_overdue_contracts`' `totals` buckets: same rule, same numbers (decision 8).
   - In `totals` only, each bucket also as `{ amount, principal, profit }` (the slice's "totals of principal and markup").
   - `overdue` = Σ of the four late buckets; `overdue_pct` = `overdue` / `outstanding` × 100, 1 decimal, `null` when `outstanding` is 0.
   - Counts: `contracts` (distinct open contracts with a balance), `customers` (distinct), `overdue_contracts`, `max_days_late` (of the overdue lines, `null` when none), `oldest_due_date` (earliest unpaid current line), `last_payment_at` (latest `v_effective_allocations.paid_at` with `direction = 'in'` on those contracts, as the overdue list shows it), `migrated_contracts`.
   - **No fee column.** Rule 4: there are no fees; `fees_due` is not read or shown. The SQL test asserts no `charges` row can exist (N04's guard) rather than reporting zeros.
5. **Group by** (`p_group_by`, required, one of):
   | `group_by` | Row key and label | Notes |
   |---|---|---|
   | `customer` | customer id, `full_name`, first phone, collector name | the default drill-down target |
   | `branch` | branch id, name, code | the **contract's** branch (where it was sold; owner question 6), not the customer's |
   | `collector` | employee id and name, `null` = "No collector" | the customer's **current** `collector_id` (N06; owner question 4) |
   | `contract` | contract id, number, customer name, branch, frequency, `is_migrated`, next due date | the drill-down rows; the Web links each to `/contracts/:id` |
   A row with a filter of its own dimension is the drill-down: `group_by=contract&customer_id=…` lists that customer's contracts, `group_by=customer&collector_id=…` lists that collector's customers.
6. **Who sees what.** The report needs **`report.financial`** (the baseline key names receivables reports; owner question 3). Reads work in an **expired** shop: do as `report_sales` does (`app.current_employee_id()` for a signed-in employee of the shop, then `app.has_permission('report.financial')`, else `PERMISSION_DENIED`). Branch scope as D02: `p_branch_id` NULL = every branch the caller can see (`app.has_branch_access`, inactive branches included: their contracts are still owed); a given branch must be the shop's (`BRANCH_NOT_FOUND`) and visible (`BRANCH_DENIED`). Not audited (reads aren't, D19). A collector without `report.financial` keeps using the overdue list (their own customers): this report adds no access for them.
7. **Filters.** `p_collector_id` = an employee id (`EMPLOYEE_NOT_FOUND` if not the shop's) or the literal `none` (customers without a collector). `p_customer_id` (`CUSTOMER_NOT_FOUND`). `p_q` (customer and contract groupings only, else `VALIDATION_FAILED: q`): the overdue list's search (contract number prefix, name, phone, exact national id; at most 100 characters, `%` and `_` escaped). `p_min_days` 1-100000: keep only the **contracts** whose `max_days_late` is at least that (as the overdue list's `min_days`); NULL = every open contract, overdue or not. Every id of another shop answers its `*_NOT_FOUND`, never data. A filter narrows the rows, the totals and the check alike.
8. **Totals and the check (the slice's Done when).** `totals` is computed **from the contracts, not from the rows**: Σ `v_contract_balances.remaining` of the open contracts in scope (after the filters), with `principal` from `principal_outstanding`, and the buckets from `v_receivables_aging` for the same contracts. `check` answers `{ rows_match: boolean, contracts_checked: integer, differences: { outstanding, principal, not_due, late_1_30, late_31_60, late_61_90, late_90_plus }, overdue_list_match: boolean | null }`: the sum of the rows of **all pages** (in SQL) minus `totals`, which must be exactly 0 (every value is already 2 decimals: a difference is a bug to report, not to hide); and, when no `customer_id` / `q` / `min_days` filter is given, whether Σ of the late buckets equals `list_overdue_contracts`' own `totals.overdue_amount` for the same branch / collector scope (`null` otherwise, because the overdue list has no such filter). An open contract with no current schedule line is not a balance this report can age: count it in `check.contracts_without_schedule` and make `rows_match` false (it should never happen; R02's `customer_contract_total` has a fallback for it).
9. **Sorting and paging.** `p_sort` one of `outstanding_desc` (default), `outstanding_asc`, `overdue_desc`, `late_90_plus_desc`, `max_days_late_desc`, `key_asc` (the label: name, number). Ties by the key, then the id. `p_page_size` 1-1000 (the Web's export uses 1000), `total_count` = rows of the whole result. `totals` and `check` always cover the whole result, not the page.
10. **Speed.** Under **500 ms** for the seed shop and under **2 s** for a shop with 20 000 open contracts / 240 000 schedule lines / 150 000 allocations (measure on the local stack with a generated set, as D01 and D02 did, and write the numbers in D91). `v_schedule_line_status` computes paid amounts over the whole shop: restrict it to the open contracts' current lines first (a CTE of the open contract ids joined early, or the same definition inlined for those lines), and **prove in the SQL test that your set equals the view** line by line for the test shop. Add an index only if a measured plan needs it and say which. No summary table, no cache.

## Owner questions (the owner confirmed every recommended answer on 23 Oct; record them in D91)
1. **Grace days:** a line inside its policy's grace days counts as **not due** and becomes late only after grace, with days late counted from the due date (exactly the overdue list, the dashboard tile and the customer page), *or* every line past its due date is late from day 1, ignoring grace (the report would then disagree with the overdue list). → **Follow N04 (grace first).**
2. **Date:** the report shows **today** only, *or* also lets you pick a past date (needs payments and schedule versions rebuilt as they stood: a much bigger task). → **Today only.**
3. **Who can see it:** holders of **`report.financial`** (owner and accountant by default; grantable), *or* also branch managers through `overdue.view`. → **`report.financial` only.**
4. **Collector grouping:** by the customer's **current** collector (moving a customer moves their whole balance), *or* by the collector at the time of each sale (needs a snapshot column: a schema change). → **Current collector.**
5. **Written-off contracts:** left out (they are closed; nothing is owed any more), *or* shown in a separate "written off" column. → **Left out.**
6. **Branch of a balance:** the branch where the contract was **sold**, *or* the branch the customer pays at most often. → **The selling branch.**
